## 2. 哪些可以借鉴（按价值排序）

1. **🔴 OntoOS 交互式推演沙盘（最大借鉴，也是最大缺口）**——把我方散落的积木（SimClock + generic_inference + risk_timeline + temporal + 派生 + Action）**整合成一个有状态的沙盘会话**：载世界基准+范围 → 逐 tick 推进 → 状态变量更新 → **风险沿 link 图按系数+延迟传导** → 中途用业务动作干预 → checkpoint/回滚 → 场景分支 → 多时间线 KPI 对比。这是从"算一张曲线"升级到"活一遍世界"。
2. **🟠 "三件套→可进入推演"显式门禁 + L0-L4 认证 + Trial Tick**——把我方 A10/A18/闭包**产品化**为：①显式"规则+动作+查询三件套齐"门 ②L0-L4 认证阶梯 + 仿真试 tick（触发规则验证真能跑）③Fanout 安全/Writeback 完整/Observability 达标三准则。比我方现有闭包门更直观可信。
3. **🟠 仿真准备度评分（全局+逐实体，结构/知识/行为三维）+ Health/Trust 雷达**——把我方 FDE 节点缺口码升级为**量化评分 + 雷达可视 + 逐实体 75/100 待补全**。直接喂 G-9 发育闭环的"准备度"展示。
4. **🟡 沙盘可视化（图上节点色风险 + 传导动画 + 时间轴 scrubber）**——我方有图谱可视化与时序曲线，但缺"在拓扑图上看风险逐 tick 染色扩散"的沙盘动画。强体验、强说服力。
5. **🟡 沙盘态可变 Action（simulate-without-commit）**——业务动作分两态：**沙盘模拟态**（可变、不提交、可回滚）vs **真值态**（R4 审批写回）。当前我方 Action 只有真值态。
6. **🟡 18 问"由浅入深"教学化指挥台脚本**——把推演能力做成 7 类渐进问句模板（观测→适配→单步→传导→审计→对比→纠错），是极好的**验收脚本 + 客户上手路径**，可直接做成我方场景卡分层。
7. **🟢 WebSocket 实时数据源**——实时流注入（对供应链/风控类实时场景关键）。

## 3. 哪些我们目前无法满足（诚实缺口）

> 这些是"积木有、整层缺"，不是从零：

1. **统一的交互式时序推演沙盘（OntoOS 核心）**——缺**沙盘会话**这个一等对象与其生命周期（初始化三步→逐 tick→干预→checkpoint→分支→对比）。我方现状是"一次性求解器曲线 + 单步 what-if"，**非"有状态、可交互、可回滚、可分支"的世界仿真**。
2. **时序风险传导（系数 + 延迟，沿真实 link 图逐 tick）**——我方派生瞬时重算、规则是门禁、risk_timeline 是单发曲线；**缺"风险在拓扑上按系数和时延一跳一跳流"的传导引擎**。
3. **仿真态 checkpoint / 回滚 / 多场景时间线分支 + KPI 对比**——缺交互仿真的存档恢复与分支比对。
4. **L0-L4 认证 + Trial Tick + Health/Trust 雷达 + 逐实体准备度**——缺产品化的仿真就绪认证与可视度量。
5. **沙盘拓扑动画 + 时间轴 scrubber**——缺沙盘级可视化体验。
6. **WebSocket 实时数据源**——缺实时流注入。
7. **沙盘态可变动作**——缺"模拟不提交"的动作语义。

## 5. 《本体引用与影响》（铁律 0）

- **对象类型**（§2）：触及 `SimulationClock/ClockTickReport`（A8，已有）、`DerivationSpec`（传导扩展）、`ActionType/ActionDraft`（双态）、`ObjectPropHistory`（temporal 回看）、`Solver`（risk/counterfactual_timeline）、`GapReport`（就绪诊断）；**新增 `SimSession`（推演沙盘会话）**。
- **链路**（§3）：新增**沙盘链路** `SimSession --init(基准+范围+预检)--> 世界态 --tick--> 派生传导(系数+延迟) ⊕ Action(模拟态) --> 状态更新 --checkpoint/branch--> 多时间线 --compare--> KPI`。当前我方编排链是"问句→求解器→答案"（一次性），**沙盘链是新增的有状态时序链**。
- **不变量**：R6（沙盘同基准+同范围+同操作序列=字节一致，确定性仿真）、R4（沙盘态可变但写真值仍经审批）、R13（每 tick 状态变动可溯源）、R16（仿真就绪认证接发育闭环三环）、R3（沙盘 entitlement 门禁）。
- **断点**（§8）：与新登记 **G-9（场景卡发育闭环）/ G-10（规则即引用）** 强相关——沙盘的"传导系数"正是 G-10 要的"规则可编辑即推演变"；沙盘就绪认证正是 G-9 要的"亲手验证才上架"。
- **回写要求**：若立项实现"推演沙盘"，须新增本体 §2 `SimSession`、§3 沙盘链路、§4 `sim.*` 事件、§7 仿真就绪门、§8 评估是否登记"无交互沙盘"断点。

## 6. 战略结论（给决策者）

- **我方相对竞品的强项**：Build 侧的**自成长发育闭环**（R16/A10/A18/GapReport/runGrowthLoop）比竞品 L0-L4 更自动；**38 个确定性求解器 + CP-SAT 可证最优**是竞品（偏衍生规则传导）未展示的硬核算力；多租户/entitlement/R4/审计成熟。
- **我方最大缺口**：**OntoOS 式交互推演沙盘**——这是竞品的"杀手锏体验"（活一遍世界、看风险扩散、随手干预、分支比对），我方有全部积木却缺这一整合层。**这是 P0 级战略补强项**。
- **最高性价比借鉴顺序**：① 推演沙盘会话（整合积木，最大价值）→ ② 仿真就绪认证 + 雷达（产品化我方已有闭包）→ ③ 时序传导派生（接规则即引用）→ ④ 沙盘可视化动画 → ⑤ 实时数据源。
- **诚实边界**：本分析基于竞品**一份图文文档**（非实跑竞品），其"准备度评分/认证"内部口径不可见；我方"积木齐全"是代码锚定的事实，但"整合成沙盘"的工作量不小（新一等对象 + 时序传导引擎 + 前端沙盘 + AI 指挥台对接），需专项 PRD 评估。

> 下一步可选：把"推演沙盘（OntoOS 对位）"展开成一份完整 PRD（含 SimSession 契约/沙盘链路/时序传导引擎/就绪认证/前端/验收），其他 agent 可遵循开发。
