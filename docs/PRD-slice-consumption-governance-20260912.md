### 前置 C · `resolve_slice` 收敛回执的形状（Agent 线核心裁决）

工具结果从「整包 nodes+edges 直灌」改为收敛形，两种收敛力度：

| | 回执形状 | 适用判断 |
|---|---|---|
| **C1** | `{类型×跳数计数表, 根节点全量 props, 深层节点只给 id+typeKey, truncated}` + 提示 agent 用 `query_objects` 下钻 | 保留"图存在且多宽"的态势感知；深层细节靠 agent 自主下钻（渐进披露） |

**建议 C1**。无论选哪个，`evals.ts`/hand-run 套件里凡断言 `resolve_slice` 回包结构的用例都要跟着改（影响面排查列入工单）。

```

                                                                 │
        ┌────────────────────────┬───────────────────────────────┴──────────────┐
```

- **R13（派生投影只读）**：库是投影，写唯一口是既有 `putSliceSpec`（outbox 发 `slice.planned`），不新开口。

## 2 · 背景与证据（全部实测，2026-09-12 demo 租户）

1. **两页并列、功能重叠**：`adminRegistry.ts:60-61` 同挂「建模与图谱」组；两页各内嵌一个 `planSlice` 规划器，共享 `SliceInspector`。

2. **价值链断在半截**：`POST /a/v1/slices/library/build`（admin 幂等全量登记，`app.ts:6197`）**前端零调用**（seam 门 149 零调用清单在册），库页只有 GET。
   > ✅ **审核方复验成立**：端点在 `app.ts:6197`；`grep -rn "library/build" apps/frontend-shell/src` **零命中**。
   > 金丝雀：同法查 `slices/library`（GET）在前端**有**命中 ⇒ 查法没坏，是那一条真的零调用。

3. **节点实测**（真实 `SO-3391` 解析）：domain_d06_capacity **834** 节点 / enterprise_360 **570** / order_to_cash_720 **562** / order_fulfillment_360 **534** / domain_d04_product 397 / domain_d03_sales 280 / domain_d05_material 139 / order_to_material_bom 101 / equipment_impact_360 73；107 条切片中 **54 条 >10 节点**。
   > ⚠ **审核方未复验**（需真起服务解析，本次未起）。这些数**驱动 AC4 的验收**，故工单第一件事就是**重测这一组**；
   > 与本 PRD 记录不符时**以实测为准并回写本节**，⛔ 不许照着旧数写验收。

   > ✅ **审核方复验成立，逐字核过**：`:328` 是 `case "resolve_slice": return this.deps.dataCore.ontology.resolveSlice(...)` —— **回包原样返回，零收敛**；
   > `:315-326` 的 `retrieve` 确实只留 `kind/key/label/description/score/scoreBreakdown`，注释原文就是「不回灌全 resource 体·省 token」。
   > **这是本 PRD 最硬的一条证据：同一个文件里，正确做法与错误做法相隔 13 行。**

6. **spec 自带节流阀全闲置**：`limitPerNode`（默认 50，`ontology-core.ts:690`）、`project` 列选（`:646-655`）、`filter`——battery 9 条业务切片**一道未设**；且 `limitPerNode` 对"浅而宽"扇出（每父仅扇出数个）天然无效，**有效的是 `project`**（每节点字节砍约八成）。
   > ⚠ **【本版改动 ③】这一条降为「待自证前提」，⛔ 不许照抄。**
   > 审核方全文件 grep `apps/datacore/src/synthetic/battery.ts`：`project:` **96 处**、`limitPerNode` **50 处**。
   > 这**不构成否定** —— 那些命中很可能落在别的对象/别的结构上，不在那 9 条切片里。

## 3 · 目标 / 非目标

**目标**
- G1 「本体切片」收编三页签：**已登记 | 切片库 | 路径规划**，页签切换不跳路由；两规划器并一。
- G2 登记链路接通：库行「登记为切片」（前置 B）+ 顶部「全部登记」（`library/build`）+ 已登记章（幂等可重入）。
- G3 撤销「切片库」导航位（前置 A）。
- G4 人看防淹：默认视图 `biz.*` 归组折叠（不与手工切片混排，`coverage_*` 现状行为不变）；内联子图按跳折叠——默认展开前 2 跳，深层按类型分组计数（"Process ×200"）点击展开。
- G5 **Agent 回执收敛**：`resolve_slice` 改收敛形（前置 C）。
  > **【本版改动 ②】消费面措辞收紧。** v1 写的是「消费面仅限 agentcore executor 出口」。
  > 审核方追一层实测：全仓另有 **6 处** `resolve_slice` 引用 ——
  > `ops/fallback.ts:86`（兜底计划生成器造 step）· `router/project-trace.ts:44,87,113`（步骤分类/跳数）·
  > `refs/report.ts:89`（`step.type !== "resolve_slice"` → 出向引用上报）· `dril/relations.ts:17`
  > （workflow --includes--> slice 边）· `catalog/service.ts:274`（plan 出向引用）· `evals.ts:77-78`（断言意图）。
  >
  > **准确命题**：这 6 处消费的是**步骤类型（`step.type`）**，不是**回执形状** ⇒ 改回执大概率不波及它们；
  > **回执形状**的消费面**目前只找到 executor 一处**。
  > ⛔ 但「只找到一处」不等于「只有一处」——**工单必须逐条自证这 6 处不读回执**，
  > 并对 `evals.ts` / hand-run 套件做**断言级排查**（那是唯一已知会读结构的地方）。
- G6 battery 9 条业务切片 paths 补 `project` 列选（订单号/数量/交期等关键字段），人看与 agent 双受益。
- G7 agent 侧 `resolve_slice` 可选切片目录排除 `coverage_*`（机器饲料不进 LLM 上下文）。

**非目标**
- 不改 `deriveSliceLibrary`、`executeSlice` 遍历语义、SliceSpec schema（`project/limitPerNode/filter` 全是既有字段）。
- **不拆小任何现有切片**（§2.4 论证不可行；若仓主仍要 spec 层 ≤10，需另立 PRD 论证消费方改造）。
- 不动 coverage_* 生成逻辑与覆盖率门；不动求解器场景取数路径。

## 5 · 验收标准

- **AC1** 三页签同页切换，`/admin/slices?tab=library|plan` 可直链；旧 `/admin/slice-library` 按前置 A 处理。
  **外加**：撤位后跑 `f61.admin-nav-groups` 与 `check-nav-group-coverage.mjs`，**两者均须 RC=0**，确认没造出新的孤儿条目（来历见前置 A 那条订正）。
- **AC2** 单条登记后该行打「已登记」章且出现在「已登记」页签；重复登记幂等（version+1，不报错不复制）。
- **AC3** 全部登记返回 `registered` 计数 = intra+cross 库条数，重跑幂等。

- **AC4 【本版改动 ④：阈值 → 对照实验，四个数】**
  v1 写的是「534 节点切片默认只渲染前 2 跳（首屏节点数 <50）」—— 那是**阈值**，答不了
  「折叠是**按跳**生效，还是一刀切砍到 50」。二者屏上长得一样，但后者在小切片上会**砍掉本该全显的内容**。

  **判据（写死）**：取**两条规模差一个量级**的切片，各测改前改后，**四个数缺一个不算交付**：

  | 切片 | 全量节点 | 改前首屏节点数 | 改后首屏节点数 |
  |---|---|---|---|
  | `domain_d06_capacity`（大） | ~834（**须重测**，见 §2.3） | ? | ? |
  | `order_to_material_bom`（小） | ~101（**须重测**） | ? | ? |

  **可预言的变化**：大切片必须**显著下降**；小切片若其前 2 跳节点数本就 <50，则**改后应与改前相同或接近**
  （证明折叠按跳走）。**小切片也被砍到 50 ⇒ 是一刀切，判不通过。**

- **AC5 【本版改动 ①：改前量必须实测】**
  `resolve_slice(order_fulfillment_360, {so})` 回执按前置 C 形状。
  **改前 / 改后各实测一次回包字节数（`Buffer.byteLength(JSON.stringify(回包))`），报告给两个数。**
  > ⛔ v1 的「~3.5 万 token」是**估算**（口径：样例节点 ~250B × 1107 元素），**不得作为验收基准**。
  > 形态：「我用『样例字节 × 元素数』当作『真实 token 量』的证据，而前者并不度量后者。」
  > **目标**：改后 < 改前的 **1/10**，且改后回包字节数 **< 12 KB**（≈3,000 token 的字节口径，
  > 中文 UTF-8 按 3 B/字符估 —— **这个折算本身也是估算，故验收判据落在字节数上，不落在 token 数上**）。
  >
  > **外加**：深层 id 可用于 `query_objects` 二次下钻成功（证明 C1 保留了锚点，不是 C2 的盲态）。

- **AC6** project 列选生效：同一切片同参数，节点 props 只含列选字段（**前后对比取证，给两个数：改前每节点平均字节 / 改后每节点平均字节**）。
- **AC7** agent 切片目录不含 `coverage_*`（目录输出取证）。
