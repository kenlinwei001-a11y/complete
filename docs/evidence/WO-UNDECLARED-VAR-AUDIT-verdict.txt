§2 · 主线索裁决：`PurchaseOrder.procurementDelay` 全负，打死了哪条分支？
────────────────────────────────────────────────────────────────────────────────
【结论 A】打死的**控制流分支 = 0 条**。逐条排除，全部有运行期读数：
  · B1 `sourceVal === 0`：tick0 30 格无一为 0 ⇒ 不命中（trace 实测该边每拍 **30/30** 条贡献）
  · B2：该规则 reaction=null ⇒ `drive = sourceVal ≠ 0`
  · B3/B4/B5：均不命中；B6：该规则 clamp=null
  · 该边的贡献**非零且真的在驱动下游**：Σ=−1.775558/拍，靶格 Material.shortageRisk 158 格
  ⇒ 不是「边哑火」，是「边在按反方向推」。**「值恒负」打死的控制流分支：零条。**

【结论 B】它打死的是**一条数值上的半轴**，位置点名（行号为本次树内坐标，会漂）：
  文件/符号  apps/datacore/src/solvers/chain-loss.ts 的 `simDeltaDaysFor()`
  行        `return { stateVar, stateValue: cell, deltaDays: Math.max(0, cell) };`   ← 本次读为 **:400**
  消费点     `const days = baseDays + (simAdd?.deltaDays ?? 0);`                     ← 本次读为 **:931**
  条件       `cell < 0` ⇒ `deltaDays ≡ 0` ⇒ **「提前到货 N 天 ⇒ 这条腿少 N 天」这个方向
             结构性不可达**，与数据无关（clamp 把所有负值映到 0，一行代码删掉一个半轴）。
  今天的种子数据让这条被 clamp 掉的半轴**对 PurchaseOrder 腿完全生效**：
    零扰动臂 Z3 · chain-loss-matrix.simContext.appliedSteps：
      material.in_transit         procurementDelay   stateValue=-4              deltaDays=0
      material.iqc                queueDays          stateValue=22.884984735    deltaDays=22.884984735
      material.supplier_leadtime  deliveryDelay      stateValue=2               deltaDays=2
      appliedDays = 24.884984735（= 22.884984735 + 2，**PO 腿贡献恰好 0**）
    ⚠ 这里的 24.884984735 不是「猜」：它是 22.884984735 + 2.000000000 的精确和，PO 腿那一项是 0。

【结论 C】但这**不是「值恒负」造成的，是设计造成的**。判决实验把两者分开了：
  臂 F3（30 张 PO 的 procurementDelay 全体 `set 3`，负→正翻转）：
      material.in_transit         procurementDelay   stateValue=3               deltaDays=3
      appliedDays = 27.884984735   （差 **+3.000000000**，恰为翻转值）
  ⇒ `Math.max(0, cell)` 是**活代码**（随输入变），今天 Z3 的 `deltaDays=0` 是**数据态**
    （种子世界里 PO 全部早到），**不是结构态**。
  对照臂（同一支实验的两份对照，缺一份都不构成结论）：
      · 零扰动臂 Z3：appliedDays = 24.884984735，PO 腿 stateValue=−4 / deltaDays=0
      · 无关扰动臂 C3（18 个 FGI coverDays set 200）：appliedDays = 24.884984735，**与 Z3 逐位相同**
      · 无关扰动臂 L3（23 张负 leadDays 的 Order set 30）：appliedDays = 24.884984735，**与 Z3 逐位相同**
  ⇒ 「+3」是 PO 翻转引起的，**不是「任何扰动都让链损动一动」**。

【结论 D】三态定性（铁律 0.5 的三分法，逐条对着运行期读数说）：
  · **不是「没接线」**：`chainLossMatrix` 回包里有 `simContext.appliedSteps[]` 具名字段，
    承载映射 `SIM_DAY_STATE_VAR_BY_CARRIER.PurchaseOrder = "procurementDelay"` 与派生式
    `purchaseorder_procurement_delay = arriveDay − etaDay` 对得上；`excluded[]` 里
    `Supplier.procurementDelay: OTHER_CARRIER` 也说明映射是有意设计的。
  · **不是「接了线接错地方」**：两条腿（PurchaseOrder / Supplier）都在 `appliedSteps` 里，
    `Supplier.procurementDelay` 被显式排除在 OTHER_CARRIER 之外并给了理由 —— 不是挂错挂载点。
  · **是第四态：接了线、跑得动、被 clamp 吃掉了一整个半轴，而今天的输入恰好整批落在那个半轴。**
    即本仓 mutation-dud 条目的**第二形态：被加项恒 0 ⇒ 加号是装饰品** ——
    加号在源码里、控制流可达、mutation 掉它会红（F3 就是那个反证），
    但**今天的每一次真实调用拿到的都是 0**。

【结论 E】关于「负数是否合理」——⛔ 不按名推断。运行期能说的是：
  符号约定出自派生式 `purchaseorder_procurement_delay = arriveDay − etaDay`（负 = 早于预计到货），
  而该边系数 **+0.07928545** 让「早到 ⇒ 缺料风险下降」，两处**内部自洽**、方向一致。
  是否有业务缺陷属口径问题，**本单不下判**（本单只回答「有没有分支被值打死」）。

§3 · Order.leadDays 的第二消费方（额外发现，逐条定性）
────────────────────────────────────────────────────────────────────────────────
`apps/datacore/src/solvers/chain-impediment.ts` 的 `readBaseContention()`：
    if (!Number.isFinite(qty) || !Number.isFinite(lead) || !(qty > 0) || !(lead > 0)) { skippedOrders++; continue; }
    const prev = byType.get(bt);  byType.set(bt, prev === undefined ? qty / lead : prev + qty / lead);
  ⇒ 这是**读 props、不读世界态**的第二个消费方（`qty/leadDays` 当日产率）。
运行期真读（两条互为独立的读数）：
  · 直接读对象库：`Order` 共 **500** 张，`props.leadDays ≤ 0` 的 **373** 张，值域 [−180, 178]；
    这 373 张的 status 分布 = `{COMPLETED: 350, IN_PRODUCTION: 23}` —— **没有一张是 OPEN**。
  · `readBaseContention` 只收 `status === "OPEN"` 的 **50** 张；其中被 `!(lead > 0)` 挡下的 = **0** 张。
  · 求解器回包 `chain_impediments.data.contention`：`verdict=CONTENDED`、`basesScanned=13`，
    note **未拼接**「另有 N 张订单…被排除」一句 —— 而该句**只在 `skipped > 0` 时**拼接。
  ⇒ **守卫今天 0 命中**：负 leadDays 全部被**更早**的 `status !== OPEN` 过滤挡掉了。
  ⇒ 裁决：**无缺陷**。负值没有打死这条链上的任何分支。
  ⚠ 顺带订正我自己的一个错判：我在读源码后写下的候选结论「23/150 张负 leadDays 的订单被显式跳过」
    是错的 —— 那个 150 是 **sim 世界**的订单数，而该函数读的是**对象库**且只收 OPEN。
    形态：「我用『sim 世界里 23 张负 leadDays』当作『会被 chain-impediment 守卫跳过的那批』的证据，
    而前者并不度量后者。」已作废，不写进结论。
