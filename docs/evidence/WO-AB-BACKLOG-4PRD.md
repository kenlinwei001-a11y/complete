## WO-1 · 业务增益的独立出处（「正确」的定义）

### 现状（实测）
全仓 23 条 `demo_*` 传导边，业务增益**已有声明**且与实现可机检（`WO-AB-EDGE-GAIN-CHECK.mjs`，23/23）。
**但其中 8 条是从系数反推填的**（`增益 = 系数 ÷ 0.37`），只有 13 条是原本就在描述里的。

### 根因（5 个为什么）
1. **为什么「正确」判不了？** —— 现有判据是「实现符合描述」。
2. **为什么描述不足以判定？** —— 因为那 8 条描述里的数**是从实现反推的**，描述成了实现的镜子。
3. **为什么是反推的？** —— 原始增益**从未被业务声明过**（`battery.ts` 的 `PROPAGATION_COEF_PARAMS` 直接给了系数）。
4. **为什么没声明？** —— 种子铸造系数时，**没有「业务增益」这个槽位**；系数被当成自由参数。
5. **为什么没有槽位？** —— 建模时把「系数」理解为**调参量**，而不是「业务承诺的实现形式」。

**⇒ 根因 = 传导系数缺少「业务承诺」这一槽位，于是系数成了第一真相，描述成了第二。**

### PRD
- **目标**：每条边的增益能回答「**谁定的、依据什么、什么时候定的**」，而不只是「等于多少」。
- **判据**：随机抽一条边，能在仓内指出它的业务出处（会议 / PRD / 业务方口径），而非 `battery.ts` 的赋值行。
- **范围**：23 条 `demo_*` 边；先补 8 条反推的。
- **⛔ 不做**：不改系数（那是建模决策）；不把「反推」说成「已声明」。
- **⚠ 前置**：需要业务方输入 —— **本单做不了**，只能把缺口与清单交出去。

## WO-2 · 多扰动横向一致性

### 现状（实测）
`P2 Material.priceShock` 正幅度：检查 171 格 / 超差 46；`P3 Line.utilPressure`：73 格 / 超差 72。
**改前臂（4053）同样不成立**（67/173、75/75）⇒ **不是本单引入的。**
而**同一扰动的不同幅度**严格线性（两轮 3 次测试：比恒 10.000000）。

### 根因（待判，三类候选）
1. **域钳位**：压力族 `[0,100]`，正幅度易撞界
2. **未收敛**：`λ=0.37`，10 拍 residual `0.63^10 ≈ 0.9%`，两臂收敛速度差会在比值里显形
3. **非线性边**：`combine: "max"` 类

**⇒ 根因**尚未判定 —— ⛔ **本单不猜**。判据：跑三组不同 `TICKS`（5/10/20/40），若超差数随拍数下降 ⇒ 未收敛；若不降 ⇒ 钳位或非线性边。

### PRD
- **目标**：目标原文「输入多个扰动因素也可以推演正确」成立。
- **判据**：三臂（单 A / 单 B / A+B）各自线性；且 **A+B 的响应可由 A、B 独立预测**（可加性）—— 若引擎非线性，则须**声明不可加**并给出正确读法。
- **第一步**：按上面判据判类型（不判不动手 —— 本单已因"没看清就动手"返工多次）。
- **⛔ 不做**：不为了让比值好看而调 `λ` 或域上界。

## WO-3 · 三行钱真机实拍

### 现状
三行钱（成本/毛利/应收）已接通（`Console0828.tsx:980` 起，「原恒 `nocalc`」），
`FE_BUILD_RC=0`，接缝测试在册。**但缺一次真实浏览器实拍** —— GOALLOOP 自陈 NOT-MEASURED。

### 根因（5 个为什么）
1. **为什么没实拍？** —— 本机 playwright 装不上：`mac13` 上 `1.63.0` 要 `chromium-headless-shell-1243`，缓存里只有 `-1208`。
2. **为什么装不上？** —— playwright 官方不支持 `mac13` 的该构建。
3. **为什么非要用它？** —— 因为「界面可见=验收标准」要求逐面 dump 屏幕真实文本。
4. **为什么没有替代？** —— 有（curl 资源链 + API 冒烟 + pid 换代），但**那验的是链路，不是"用户看见的字"**。
5. **为什么替代不够？** —— 因为三行钱在屏上是**条件渲染**（`projection.kind === "ok"` 才出数，否则显示「本次无法计算」+ `why`）——**渲染分支没被真机走过**。

**⇒ 根因 = 验收判据（界面可见）与本机能力（无可用无头浏览器）不匹配，且替代路径不覆盖渲染分支。**

### PRD
- **目标**：在真实浏览器里、对「提前交付 3 天」场景，dump `c0828-*` 三行钱的**真实文本**。
- **判据**：截图 + 文本，且**同时覆盖两条分支**（有数 / 「本次无法计算」）。
- **路径**：换一台能装 playwright 的机器 · 或改用系统 Chrome + CDP 驱动 · 或引入可用的 headless 替代。
- **⛔ 不做**：不拿 API 冒烟冒充屏上验收。

## WO-4 · 统一推演控制台降层（44 处）

### 现状
`Console0828.tsx`：`first=340 · deferred=218 · formula=0 · prose=21 · sizes=3`。
**`first=340` 比存量榜第一名（`GlobalSimView` 211）还高 61%，而它不在门的账上。**

### 根因（5 个为什么）
1. **为什么这页没降层？** —— 它不在 `ui-first-layer-baseline.json` 的 `files` 或 `unlisted` 段。
2. **为什么不在？** —— 门有 D6 判据该报「未落账」，**报了别人（`CellExplainPanel`/`DecisionConsoleView`）却没报它**。
3. **为什么门跳过它？** —— **未查明**（`EXCLUDE_RE` 为空、它是 `.tsx`、在 `SCAN_ROOT` 下、`--explain` 能算它的读数）。
4. **为什么没被发现？** —— 门自己的金丝雀 `MIN_FILES=150`（现算 182）**发现不了少一个**。
5. **为什么金丝雀发现不了？** —— 它守的是"枚举器整体坏了"，不是"某个文件漏账"。

**⇒ 根因 = 门的记账缺口：一个文件能被 `--explain` 算出读数、却不进任何基线段，且无判据守这一档。**

### PRD
- **目标**：`Console0828` 进账、受同一套棘轮；且**这一类缺口今后可机检**。
- **判据**：① `--explain` 能算出的文件，必在 `files` 或 `unlisted` 之一（否则红）；
  ② 降层后 `first` 降、`deferred` 升、**总量不掉**（守 D4「静默降层等于删除」）；
  ③ 判据优先级 `formula > sizes > prose > first`（沿用门既有口径）。
- **⚠ 边界**：修门可能触碰**禁令 3（新增门/棘轮/基线 JSON 冻结）** ⇒ **需仓主裁决落地形态**。
- **⛔ 不做**：不自造第二套分档（本单已犯过 —— 我自创的"三档"与仓内既有口径形态不合）。
