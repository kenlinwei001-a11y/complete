=== WO-1 · 传导系数的「业务增益」为什么没有独立于快照的出处 ===
轮次 R1（从零开始追）· 2026-10-07 · 分支 claude/semantics-declared · 后端 4052
接手前提不采信：上一轮的「0.295455 = pos_ncm 的 BOM 成本占比（出处存在但会过期）」本轮被推翻（见 §推翻）。

  key        demo_material_price_to_model_cost
  系数 c     0.109318171                 （GET /a/v1/sim/propagation-rules）

  落点       Model.costPressure（该格入边共 3 条：material / leaddays / wo_release）
  屏上原话   「物料涨价 ⇒ 用它的型号成本上抬（价格冲击 × 0.295455 = 型号成本压力）」
  本格入边意图档位：0.65 + 0.5 + 0.5 ⇒ S_g = 1.65（三条 W 均 = 1）
  ⇒ 闭式：稳态增益 = 0.65 × min(1, 0.75/1.65) = 0.65 × 5/11 = **13/44 = 0.2954545…** → 6 位 = 屏上那个 0.295455

【结论（一句话）】
「业务增益」根本不是被承载的量，而是**系数的一个显示投影**（= 系数 ÷ λ）；系数本身 = 手写档位 0.65 × 该格反饱和折减 f_g(0.75/S_g) × λ，
三层里没有一层来自业务事实。仓内两种现成的「出处承载范式」（值域 source 必填 / 分摊口径在册表）都只长在**关于数据**的声明上；
**「强度」这一档既没有格子、也没有纪律、也没有消费方** ⇒ 「独立于快照的出处」在这个结构下不可能出现 —— 不是没填，是没地方放。

【十问十答】
1. 为什么这个「业务增益」没有独立出处？
   答：因为它不是从业务事实算的，是「手写档位 × 引擎折减」的乘积：
       0.65（2026-08-10 建边时敲的裸字面量）× f_g(0.75/1.65，反饱和预算)。两个因子都不是业务量。
   证据：battery.ts:776 `PROPAGATION_COEF_PARAMS: Record<string, number>`；seed.ts:649-651 注释自陈
        「稳态增益 = 0.65 × 0.4545455 = 0.295455」；首版边块无 description（见 3）。

2. 为什么 0.65 没有出处？
   答：因为建边时它被当成「调参量」直接敲进去，从未有业务口径声明过它。
   证据：`git show 44f1bd396:apps/datacore/src/seed.ts` 该边块只有 `coefficient: 0.65`，连 description 都没有；
        description 首次出现于 2828199b5（2026-08-28），且直接照抄 0.65（「价格冲击 × 0.65」）。
        全表当时的系数是 10 个离散「人手档位」值（docs/SIM-UX-BACKING.md:45：-0.6,0.3,…,0.65,0.9）——手调指纹。

3. 为什么后来补了描述、补了预算、补了 23 条增益声明，仍然没有出处？
   答：因为后续补的全是**一致性**，不是**出处**：改系数时把描述一起改（或事后补齐），方向恒为「实现 → 文案」。
   证据：c2fba43ea（2026-09-17）系数与描述一起变 0.423913；b8461379e（10-01）只改系数；
        8b26efe48（10-02）提交信息原话：「改系数漏改的屏上描述串 …… 该串经 GET 原样下发到屏上 = 屏上正在说与实际不符的话」。

4. 为什么判据只能做成「一致性」？
   答：因为仓里没有第二个量可以对照。0.295455 全仓只出现 3 行，全在 seed.ts（注释 2 行 + description 1 行）。
   证据：`grep -rn "0.295455" apps packages docs --include=*.ts/tsx/json/md`（排除 dist/evidence）⇒ 3 行，全在 apps/datacore/src/seed.ts:648/650/651。
        正向对照（防「找不到=没有」）：同一把尺子 `grep -rln "0.222" docs/*.md` 命中非空（docs/SYSTEM-ONTOLOGY.md）⇒ grep 本身是活的。

5. 为什么没有第二个量（承诺记录）能挂出处的表格？
   答：因为**写路只收数字**。编辑者能改的只有数，不能随数一起挂「谁/何时/依据」。
   证据：app.ts:363 `RuleCreateSchema.params = z.record(z.string(), z.number())`（POST/PUT /a/v1/rules 的入口）。
        种子路径的 params 类型其实允许 string/string[]（contracts/datacore.ts:660），但 50 条边无一使用，也没有任何消费者读它 —— 格子能放，纪律与消费方不存在。

6. 为什么「承诺」不是本体里的对象？
   答：因为规则库自陈是**参数载体**：「参数载体而非判定规则：50 条传导边系数的唯一可编辑来源」（battery.ts:1148）。
        「可编辑」被实现成「一个数」，这是设计选择（C35/C36 存在的唯一理由就是让 λ/系数可编辑）——所以这两张表里天生的只有值。

7. 为什么这个缺口一直静默？（没人发现）
   答：因为同一份代码里**相邻的两类数值声明都有必填出处**，唯独系数没有，而没有判据把三者对齐：
        · 值域：`StateVarDomain.source: z.string()` 必填，契约原话「这个取值域的出处（哪一句注释、哪个生成式定的）。**写不出出处就不许声明**」（contracts/sim.ts:1128-1129）；
          实测其内容是**数据推导**：如 qualificationQueue 写「certHours med=134h÷24=5.58 天（n=18，2.1–8.0）⇒ λ=1−0.25^(1/5.58)≈0.22」（battery.ts:3891-3892）。
        · 分摊口径：在册注册表 `PAIR_WEIGHT_BASIS_REGISTRY` + `isKnownPairWeightBasis` 拒自由串 + 每条口径带 measure 文本（contracts/sim.ts:110 起）。
        · 系数/增益：`Record<string, number>`，无出处字段、无在册表、无复核日期、无判据。
        ⇒ 「写不出出处就不许声明」这条纪律只长在值域与口径上，**强度没被覆盖**。这是「没有承载物」的硬证据。

8. 为什么这条纪律没长到系数上？
   答：因为两项身份不同。值域/口径答的是「这个量是什么、范围多少、从哪个字段取」——都是**关于数据**的声明，天然指得回数据；
        系数答的是「机制多强」，被当作**工程调参**，工程参数的传统形态就是一个数。当显示层用「÷λ」把它改名成「业务增益」讲给用户听时，
        没有任何东西随这次改名落位。

9. 为什么改名之后没人要求补出处？（那批「增益声明」为何整批过关）
   答：因为那批数是从实现反推的，且反推用的 λ 是全表常数 0.37 —— 而本仓自己已立账 λ 逐格不同（0.37/0.75/0.22，seed.ts:283-288 订正②）。
        ⇒ 反推当场写出与引擎不符的数：`demo_model_demand_to_cert_queue` 屏上 ×0.178378，引擎真值 0.066/0.22 = **0.3**。
        仓内真门（逐格 λ）`edge-money-weight.seam.test.ts` §3 实测**红**：`描述 ×0.178378 vs 真值 0.3`（本轮亲跑，RC=1，见 WO1-SEAM3-RED.txt）。
        ⇒ 连「实现一致性」这一侧都没过：那批「业务增益」不是被**声明**的，是被**投影**的；投影的全部输入都在实现里。

10. 为什么没有承载物？——追到底
   答：因为「业务增益」在这个系统里**从来不是一个独立的量**：它是系数的显示投影（= c ÷ λ），而系数 = 手写档位 × 引擎反饱和折减 × λ。
        没有任何字段/表/记录类型承载「这条边的强度由谁、在何时、依据什么定」；仓里现成的两种出处范式都只覆盖「关于数据」的声明，
        强度被排除在外。⇒ 「独立于快照的出处」不只是今天没有，而是**结构上不可能出现**：
        数据的出处可以指向数据（会过期，但可重算）；强度的出处必须指向**记录或公式**，而记录与公式都没有落点。
        于是每次「让它正确」的动作只能改数（并继承上一次的取整误差，见下），每次「让它说得出出处」的动作无处落笔。

【本轮推翻的判断】
① 推翻**上一轮的结论**（接手时的第一判断素材）：「0.295455 = pos_ncm 的 BOM 成本占比（出处存在但会过期）」——三条独立反证：
   a. 值不对：0.295455 的精确值是 13/44（预算闭式，见上）；pos_ncm 占比本轮独立现算 = 0.298451952（Σ行成本 632.84），差 1.0%。两个数的关系到此为止。
   b. 没有推导链：占比**从未**喂进系数。系数两次改动（0.65 → 0.423913 → 0.295455）全部由**预算**触发（2026-09-17 建预算、2026-10-01 加一条入边），
      与任何物料价格变动无关；Material.unitPrice 在本仓是种子生成值（materials-seed.ts:89 `round(base×(0.9+rng()×0.2),2)`），
      app.ts 无 /a/v1/objects 的直写路由（对象属性变更须走 ActionDraft 裁决路）—— 而**即使有人**经裁决路改了 unitPrice，系数也不会跟随，
      因为从未有推导链把占比喂进系数。「会过期」需要一个"曾同源、今分叉"的关系，这里没有。
   c. 数值生成方式：单价 176.35 是 PRNG 出数（base 180），占比本身没有任何业务输入；把「1% 接近」读成「出处」是按数凑解释。
   （占比复算本身没错——错的是把它当成了系数的来源。）
② 推翻**我自己的第一判断**：我一开始写「根因 = 系数表缺一个『业务承诺』槽位」。深查后**不够**：
   · 「缺字段」不成立为根因：种子路径的 params 本来就允许 string（contracts/datacore.ts:660），要挂句出处是挂得下的；
     真正的缺口是「没有任何东西要求它 + 没有消费方读它 + 写路只收数」——缺的不是格子，是**纪律与消费方**。
   · 更深的一层：增益不是独立量（它是系数的投影），所以就算摆一个槽位，填进去的也只能是从系数反推的数 ——
     本轮的实证就是那个反推写出 0.178378 ≠ 真值 0.3（仓门当场红）。**槽位治不了「值没有推导源」。**
③ 附带推翻一条我自己的中间判断：我曾以为 C36 的 `params` 只能存数 —— 查了种子类型（contracts/datacore.ts:660 允许 number|string|string[]）后撤回；
   「只收数」成立的只有**写路**（app.ts:363）。

【修法】—— 承载物补在哪、以什么形态
· 主干：把「强度」从一个数改成**三件套的合成**，且合成发生在一处（读取时现算，不再手抄）：
      coefficient = intentGain × f_g(该格现算) × λ(该格 decayRef 现算)
  其中 `intentGain` 是唯一被持久化的**业务档位**；f_g 与 λ 都由当前配置现算 ⇒ 消灭两种已发生的形态
  （「改系数漏改描述」8b26efe48；「改系数用旧值 × 23/33 重缩放，继承上一次取整误差」b8461379e）。
· 承载物：给 `intentGain` 配**与值域 source 同范式**的必填出处（contracts/sim.ts:1128 那条纪律推广到强度），且出处必须是**可机检的两类之一**：
     (a) `accounting_identity`：一条对本体数据可复算的公式（本边存在候选，见下），或
     (b) `decision_record`：{定的人, 定的日期, 依据的文件/评审, 复核到期日}——到期即红，强制重新确认。
· 显示：屏上不再手写数字（seed.ts:255-258 已记账这条修法）——description 由回包里的现算增益渲染；
  并且**把折减显性化**：业务档位 / 本格折减 / 生效系数三个数并排披露（今天只有一个合成后的数）。
· 判据：门改成咬**合成关系**（coefficient == intent × f_g × λ，逐格 λ 已由 §3 做对）+ intent 出处必填且在复核期内。

【同族错测试】「这样改，同族的错还会不会以另一种形态出现？」
· 只加 `intentGain` 不要求出处 ⇒ 病变成「intent 是新的无出处数」，镜子只上移一层 ⇒ 故出处必填 + 写路校验（缺即拒收）是承重件。
· 只在屏上不写数字（只渲染）⇒ 数字不再撒谎，但「谁承诺的」仍无人认领 ⇒ 故 intent + 出处记录是承重件，渲染只是止血。
· 不把 f_g/λ 拆开显示 ⇒ 折减会被藏进 intent（今天的病：0.65 与 0.4545 混成一个 0.295455）⇒ 故三数并排。
· 残留（如实写）：出处记录可以是假的（「依据：业务方口头」），机器只能验「有没有、链接是否有效、复核期是否过期、值与推导是否一致」，
  验不了「内容为真」。这是本修法的诚实边界，不声称消除。
