链条的第一个输出，在世界诞生那一刻就已经与输入完全无关。
错误不在任何一跳的「传导」，而在 H1 的 tick0「播种」；且同一个错在链上重复了三次

H1 demo_order_leaddays_to_model_horizon

   电池型号.costPressure ─model_demanded_by_order─▶ 销售订单.costPressure

   weightRef=null  status=PUBLISHED

H3 demo_order_cost_to_customer_receivable
   销售订单.costPressure ─order_of_customer─▶ 客户.receivablePressure
   coefficient=0.03144963  combine=sum  delayTicks=0  decay=null  clamp=null
   weightRef={"basis":"source_value_relative"}  status=PUBLISHED
   描述：订单成本上去 ⇒ 该客户的应收账款压力变大
        （订单成本 × 0.084999，并按该单金额占全域平均单的倍率分摊）

H4 demo_customer_receivable_to_invoice_overdue
   客户.receivablePressure ─customer_has_invoice─▶ 应收发票.overduePressure
   coefficient=0.148  combine=sum  delayTicks=1  decay=null  clamp=null
   weightRef=null  status=PUBLISHED

⚠ 描述里的数（0.75 / 0.084999 / 0.4）是**稳态增益**，实际系数 = 该数 × λ(0.37)：
   0.75 × 0.37 = 0.2775 ✓   0.084999 × 0.37 = 0.03144963 ✓   0.4 × 0.37 = 0.148 ✓
   口径自洽，**不是病**。

§4 手算预言 vs 实测（公式 amount = 系数 × 源值 × 权重）
--------------------------------------------------------------------------------
H1：weightRef = equal_share ⇒ 权重 = 1/N（N = 该型号世界内订单数）
    SO-3391 交期 14→11，注入差 = 0.084090909 × 3 / N
    实测首现边际 = 0.010511 ⇒ **反推 N = 24.00**
    ⇒ 逐位吻合。传导算术正确。

H2：边际比 = 0.000972 / 0.003504 = **0.2774**
    规则系数 = **0.2775**  ⇒ 注入 = 系数 × 上游增量 × 权重(1)
    ⇒ 逐位吻合。传导算术正确。

H3：边际比 = 0.000220 / 0.000972 = **0.2263**
    规则系数 = 0.03144963 ⇒ 反推权重 **w ≈ 7.196**
    规则声明 source_value_relative（描述：单金额 / 全域平均单倍率）
    我按 161,135,282 / 42,371,545 = 3.803 手算 ⇒ **对不上**
    ⇒ **NOT-MEASURED：分母口径未查清，不许当已核。**

★★ 结论：三跳传导算术**全部正确**。错不在传导。

§6 四跳播种值各自的成因（形态相同、来源不同）
--------------------------------------------------------------------------------
`/world` 顶层键 = tick,state,baseProvenance（provenance 已下发）

   格                                 初值        origin      是什么
   Model.costPressure             2.926292    measured   成本占售价比（**一个率**）
   Order.costPressure                  115    measured   creditUsedRatio × 100
                                                          （**信用额度使用率，与成本无关**）
   Customer.cust_14.receivablePressure 15.745188 measured 成分待核
   ARInvoice.arinvoice_1_1.overduePressure  76   **derived**  **哈希铸造**（0–100 随机数）

   支撑读数（前次实测）：Order.costPressure ≡ creditUsedRatio × 100，150/150 逐位吻合；
   全库 6375 格中 derived（哈希铸造）2192 格 = 34%；财务投影三个入参中
   ARInvoice.overduePressure 60/60 全为 derived。

★ 每一跳各自独立犯同一个错：**把「某个比率的水平」当成「本格的偏离」放进积分器。**
  而消费端 finance-world.ts:326 按**偏离**读它：
     成本 = 基线 × (1 + 压力 ÷ 100)

§7 根因（5 个为什么）
--------------------------------------------------------------------------------
1. 为什么提前 3 天算出来的毛利不对？→ 输入只解释读数的 0.031%，其余全来自播种值。
2. 为什么播种值压倒输入？→ 消费端按「偏离」读，而生产端给的是「水平」，
   水平被整个当成了偏离。
3. 为什么生产端会放一个水平进去？→ 本格的「偏离」没有真源：
   Order.costPressure 借了 creditUsedRatio；Model.costPressure 借了成本占售价比；
   ARInvoice.overduePressure 干脆掷哈希。
4. 为什么借了没人拦？→ **全仓没有任何东西守着「一个状态量在生产端与消费端的
   语义必须一致」。**
5. 为什么没有这道守？→ 既有的门只问到「这个值真不真」，没问到
   「这个值在消费端有没有意义」。sim-real-cells.seam.test.ts 臂2 看见了并主动豁免：
      "Order|costPressure": [0, 116, "实测 40–115（n=500，越域 16 单）"]

形态（铁律 0.6 句式）：
   **「我用『这个值如实反映了它的来源』当作『这个值在它的消费端有意义』的证据，
     而前者并不度量后者。」**
