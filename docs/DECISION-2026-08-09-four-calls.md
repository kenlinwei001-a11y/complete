## ① #100 · 账期回款 60d 算不算全链前置期

### 裁决：**拆成两个指标，不合成一个数。**
- `交付前置期` = 客户下单 → 客户收货。**不含账期。**默认展示的就是它。
- `现金周转期` = 客户下单 → 回款到账。**含账期。**单列，不与前者混算。

### 实测依据
`apps/datacore/src/synthetic/cadence.ts:313/321` 里已经有一条诚实注记：
> 「`termDays` 是本节点最容易被误用的**诱饵** —— **账期 ≠ 结算节拍**，挪用即口径错标
> （本仓刚修过差 1e4 的同族错标）。」

代码里已经有人警觉过这件事，只是没形成裁决。

### 为什么不合成
合成之后账期占非增值时长 **85.5%** —— 这意味着**生产侧任何改进在这个数上都看不见**
（把 7 天的排产优化摊进 60 天账期里，指针几乎不动）。而沙盘的用途正是给生产/供应链侧做决策。
合成 = 造一个对本平台主用途无效的指标。

反过来，**删掉账期也不行**：经营层看的就是现金，`battery.ts:623` 那条「13 周现金最低点 54 亿 ·
逼近红线 50 亿」正是账期驱动的。丢了它，C18 现金红线就失去解释力。

⇒ **这正是本仓反复踩的「一个数盖住两个事实」**（铁律 0.6 的同一形态）。裁决是拆开。

### 落地
- 新增/改名两个指标口径，**任何一处 UI 显示前置期时必须标明是哪一个**。
- 加一条断言：两个指标**不得相等**（相等说明有人又把它们合并了）。
- 归入 `WO-LEADTIME-SPLIT`（待派，轻画像）。

## ② #81 · 「公司级战略方案」缺语义正确的已接线动作类型

### 裁决：**新建 `adopt_decision_play` 动作类型。不复用 `mitigation`。目标值只读不写。**

### 三条约束（缺一即返工）
1. **不许把 `decision_play` 映射到 `adopt_mitigation`。** 两者语义不同：
   `mitigation` = 针对单个风险的战术缓解；`decision_play` = 公司级多杠杆战略方案。
   映射过去 = 制造一次静默错答（本仓最恨的形态）。
2. **🔒「目标不能改」** —— 采纳战略方案**绝不许覆写 `PLAN_GOAL_TARGETS`**。
   写入的是「已采纳方案 + 其杠杆调整」，目标值是**只读对照基准**。
   这条是仓主早先定死的红线，本裁决不动它。
3. **kernel 的诚实拒绝保留为兜底。** 今天 kernel 对未映射的域**诚实不派**，这个行为是对的
   （欠账 #81 原文也这么认定）。新增动作类型之后，**兜底路径不许被削弱** ——
   将来再出现未映射的域，仍要诚实拒绝，不许静默降级到某个"最接近"的动作。

### 实测依据
欠账 #71：`G-ACTION-NOOP-EXEC` 收口至 WIRED 9 / NO_WRITE 0 / **NOT_IMPLEMENTED 1**，
那 1 条正是「采纳经营方案」（`apps/datacore/src/actions.ts:59`）。
⇒ 缺口是**一个动作类型**，不是整条链 —— 修法是补类型 + 接写端，不是重做 Action 体系。

### 落地
`WO-ADOPT-DECISION-PLAY`（待派，中画像）。判据必须是效果层：
**采纳后，方案里的杠杆真的落到了状态上，而 `PLAN_GOAL_TARGETS` 逐字节未变**（两条断言都要）。

## ④ X1 · summary 长度三处口径不一

### 裁决：**统一到 200。三处对齐。**

| 处 | 今天 | 改为 |
|---|---|---|
| 契约 `agentcore.ts:242` | `z.string().max(400)` | **200** |
| lint `skill-lint.ts:46` | `SUMMARY_MAX = 200` | 不动 |
| 前端 `SkillsPage.tsx:78` | `maxLength={400}` | **200** + 显示字数计数 |

### 实测依据（收紧是破坏性变更，先证零破坏）
```
种子 summary 条数 = 8 · 最长 = 71 字符 · 超过 200 的 = 0 条
```
⇒ **收紧到 200 打不破任何存量数据。**

### 为什么不照 body 的「两层治理」办
`SPEC §9.3` 给 body 定过两层（契约 50000 管**存得下**，lint 3000 管**该不该这么写**），
但 summary **没有对应定案**，且两者性质不同：

lint 自己的报错文案写着 —— `skill-lint.ts:287`：
> 「summary 超 200 字 …… **summary 是触发器不是简介**」

summary 会被**逐条注入 system prompt**（`agent/prompts.ts:72`
`- [${s.id}] ${s.name}: ${s.summary}`），长度**直接吃 token 预算**且随 skill 数量线性放大。
它不是「存得下就行」的字段，是**运行期成本字段**。⇒ 契约层就该收紧，不留两层。

### 今天这个不一致的真实危害
用户在界面上写到 350 字**保存成功**，点发布**被拒**。
这是「编辑期与发布期口径不一致」造成的返工，前端还不告诉他上限是多少。

### 落地
本裁决**审核方自己改**（三行的事），改在集成分支上（`SkillsPage.tsx` 已在那条分支上被改过，
落 canonical 会冲突）。加一条断言：**三处上限必须相等**，防止再次漂开。
