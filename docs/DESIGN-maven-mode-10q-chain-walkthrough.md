# 设计验证 · 10 个"全栈决策模式才答得了"的问题 × 虚拟跑全链 × 缺什么

> 用户：不急开工，先验设计。模拟 10 个**只有 Maven 式全栈决策系统（多源融合→本体→AI 推理→人机接地→行动闭环→审计）才答得了**的问题（单看板/单 SQL 答不了的），用「审核方 PRD 设计 + 目前系统」**虚拟跑全链**，逐题找断点缺什么。
> **方法**：每题沿标准链走 `多源接入→本体融合→求解器/推理→诚实位→决策接地→行动闭环→审计`，标 ✅本会话真跑验证 / 📐已设计待建 / ❌未覆盖缺口。**这是设计走查（非真跑）**——链路节点引真实求解器/路由/断点编号，结论是架构判断。

## §1 为什么这 10 题"只有全栈才答得了"

普通 BI/看板答的是"是什么"（查询既有数）；这 10 题答的是"**会怎样·为什么·该动哪·信几分·谁能动·当时为何这么定**"——需要**跨源融合 + 本体推理 + 前向推演 + 置信诚实 + 行动建议 + 可审计**，缺任一环就答不全。

| # | 问题 | 为何 Maven-only（缺哪类能力就答不了） |
|---|---|---|

## §3 缺什么（综合）

### 队列已覆盖（虚拟跑证明 D+E + 现有 WO 闭大部）
- **E1 校准活体**（Q4 信几分 / Q5 回采对账）· **E2 沙盘进日常**（Q1 杠杆择优 / Q3 情景注入 / Q6 trade-off）· **SCENE-C**（Q8 角色化 / Q6 接地）· **AUDIT-OBS**（Q9 审计）· **T5-HEARTBEAT**（生产扛多实例并发问）· **G-5**（Q10 视图跨域）。
- **结论**：**D+E + 已排 WO 队列，虚拟跑下来能闭 10 题中的 9 题最后一环**——这验证了路线图方向对、覆盖准。

### 🔴 新缺口（虚拟跑撞出·之前 WO 未充分覆盖）
**N1 · 真多源冲突仲裁（Q2）**——这是最值得补的新设计缺口：
- **现状**：`order_fullchain` 三闸（交期 C02/C03·齐套 C06/C16·财务 C15/C13/C18）是从**单一合成源**派生的三个判断；demo 全对象经单一合成连接器物化。
- **缺**："ERP 说能交、MES 良率说不能、SRM 到货说不能"这种**多源各执一词**的场景，需要：① 真多源接入（同一订单的交期/良率/到货来自不同系统）；② **跨源冲突检测 + 仲裁**（哪个源权威·缺口取并集还是最严·诚实标冲突）；③ 冲突可溯（哪个源说了什么）。
- **为何之前没覆盖**：WO-FORECAST-SIM 接了 DemandSegment/SopVersion 真源喂推演（需求侧多源），但**供给侧的"同一事实多源冲突"仲裁**没单独立项——order_fullchain 是单源三判、非多源对账。
- **建议**：立 **WO-MULTISRC-ARBITER**（P1·态势深化）——真多源接同一订单的交期/齐套/财务事实 + 冲突检测求解器（`source_conflict`）+ 仲裁策略（权威源/最严/并集·配置驱动 R14）+ 诚实标"X 源说能·Y 源说不能"。这是 Maven"多源融合"灵魂里**最硬的一块**（融合不只是拼接·是冲突仲裁）。

### ◐ 边角（够用·非命门）
- Q7 已能答（shared_bottleneck）；Q10 大部（仅视图 layout·G-5 已登记）。

## §4 一句话结论

**虚拟跑 10 题：9 题的"最后一环"被 D+E + 已排队列覆盖（路线图验证方向对）；撞出 1 个真新缺口——多源冲突仲裁（N1·Q2），是 Maven"多源融合"里之前漏立项的硬骨头，建议补 WO-MULTISRC-ARBITER。** 其余皆"大部能答·缺活体/接地/审计最后一环"，正是 D+E 队列在补。

## §5 诚实边界

- **这是设计走查、非真跑**——链路节点引真实求解器/路由/断点（多数本会话真跑验证过·标 ✅），但"10 题端到端真问"未真起服务跑（那是开工后的 FDE 实拍·本次按用户意图只验设计）。
- "✅能答"指**链路节点都在且本会话验证过**·不等于"富答案体验已实拍"（那需真 Kimi 端到端·见 SCENE-B 真 Kimi 实拍已证 agent loop 可出接地答）。
- N1 是**架构判断的新缺口**·非穷举——若 dev 指 order_fullchain 已有多源仲裁路径，给文件:行我复核。
