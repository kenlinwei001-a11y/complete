## 1. 第一问先答：仓主「看不懂它们的关系」，是因为它们**根本不是同一种东西**

这不是理解力问题，是**信息架构把三个不同层级的构件并列摆在了同一条导航里**。实测形态：

| 仓主点名的「模块」 | 它在系统里的真实形态 | 真实位置 |
|---|---|---|
| **建模与图谱** | **导航分组**（容器），内含 11 项 | `ShellLayout.tsx` `NAV_GROUPS` + `adminRegistry.ADMIN_NAV_GROUPS` 的 `modeling` 组 |
| **图谱体系** | **导航分组**（容器），内含 8 个视角，默认折叠 | 同上，`title: "图谱体系"` 那组 |
| 本体关系 | **单个管理页** | `/admin/ontology-relations` |
| 本体切片 | **单个管理页** | `/admin/slices` |
| 切片库 | **单个管理页** | `/admin/slice-library` |
| 实体合并 | **单个管理页** | `/admin/merge` |
| 边界/治理 | **单个管理页** | `/admin/boundary` |

**关键事实：「建模与图谱」这个组，把其余五个页里的四个装在自己里面。**

```
导航组「建模与图谱」（11 项）
├── 图谱视图 graph          ← 与下面那个组是同一个渲染器
├── 本体建模 modeling
├── 对象/类型浏览 object-types
├── 域管理 domains
├── 对象接口 interfaces
├── 本体关系 ontology-relations   ← 仓主点名的「模块」①
├── 本体切片 slices                ← 仓主点名的「模块」②
├── 切片库 slice-library           ← 仓主点名的「模块」③
├── 实体合并 merge                 ← 仓主点名的「模块」④
├── 边界册治理 boundary            ← 仓主点名的「模块」⑤
└── 原型 intake prototype-intake

导航组「图谱体系」（8 项，默认折叠）
└── graph-all / graph-backbone / graph-flow / graph-source
    / graph-solver / graph-mvp / graph-agent / graph-loop
```

**「图谱体系」那 8 项不是 8 个模块，是同一个组件的 8 组参数。** 实测：

- 8 个 key 全部注册在同一个渲染器上——`views/registry.ts` 只有一行 `registerRenderer("ontology-graph", …)`，8 个视角共用它；
- 8 个视角全部读同一个端点 `GET /a/v1/ontology/graph`；
- 差异**只在 `ViewConfig.options.graphOptions`**：`colorBy` / `nodeFilter.tiers` / `mvpOverlay` / `dimOthers` / `layoutSeed`（`synthetic/service.ts` 的 `graphView(...)` 逐个构造）。

⇒ **一个「按域着色 / 只看一二级 / 高亮 MVP」的下拉框，今天被拆成了 8 条一级导航项**，还外加一个第 9 个入口（「建模与图谱」组里的 `graph`）。这是仓主感觉「重合」最直接的来源：**9 个入口通向同一张图。**

> **结论 1**：仓主看不懂的不是功能，是**层级**——他被要求在同一份菜单里同时理解「一个容器」「一个页面」和「一个参数预设」。任何整合方案的第一步都不是删功能，是**把这三层分开**。

### 2.3 切片层——三个不同的东西共用「切片」这一个词

| | **本体切片** 页 | **切片库** 页 |
|---|---|---|
| 端点 | `GET /a/v1/ontology/slices` | `GET /a/v1/slices/library` |
| 条数 | **99** | **61**（域内 7 + 跨域 54） |
| 存储 | 落库（`sliceSpecs` 仓储） | **不落库**，每次请求由 `deriveSliceLibrary(types, links)` 纯函数现算 |
| 键前缀 | `coverage_*` ×95 / 四条业务键 | `biz.*` |
| **两边键的交集** | **0 条**（99 与 61 完全不相交） | |

两边的内容也不是一回事：

**「本体切片」的 99 条 = 4 条真业务切片 + 95 条单类型清单**

| 切片键 | 跳数 | 根类型 | 必填参数 | 带参解出 |
|---|---|---|---|---|
| `enterprise_360` | 31 | Order | `so` | 555 节点 / 581 边 / 18 类型 |
| `order_to_cash_720` | 23 | Order | `so` | 540 节点 / 566 边 / 15 类型 |
| `order_fulfillment_360` | 12 | Order | `so` | 531 节点 / 570 边 / 9 类型 |
| `aop_scenario_chain` | 3 | AnnualScenario | `key` | 22 节点 / 21 边 / 4 类型 |
| `coverage_*` ×95 | 0 | 各自一个类型 | — | 只有该类型的对象清单，0 条边 |

- 4 条业务切片**合计只覆盖 25 / 98 个类型**；
- **73 个类型不在任何业务切片上**，其中 **62 类有数据、承载 10,237 个对象**（占全库 12,740 的 **80.4%**）；
- 被漏掉最多的：`EquipmentOEE` 5,460 个 · `OrderLine` 873 · `InspectionResult` 520 · `ProductEquipmentCapability` 376 · `ExceptionEvent` 372 · `ProcessCapabilityWindow` 345；
- 按域看，**决策域 0/7 · 外部信号域 0/2 · 预测域 0/1 · 物料域 0/1 · 人员域 0/4 完全未被业务切片触及**。

**「切片库」的 61 条 = 把关系图重新投影了一遍，不含任何新信息**

读 `ontology/slice-library.ts` 的实现：

- `deriveIntra`：**每个域恰好一条**，根类型 = 该域内 key 字典序第一个（`biz.factory.base` 的根是 `Base`，只因为 "Base" 排第一，不是业务判断），跳数 = 根的同域直接邻接；7 条，承载 23 个类型，**彼此共享类型 = 0**（每个类型只出现在一条域内切片里）；
- `deriveCross`：**每条跨域边一条切片**，54 条**全部是 `paths=1`、`types=2`**——即 `biz.x.base_to_shipment` 就是「Base 到 Shipment 那一条边」本身。

⇒ **54 条「跨域切片」= 54 条跨域边换了个名字。** 它们不是切片，是边的清单。而域内 7 条切片彼此共享类型为 0，意味着**照现状把域切片拼起来也串不成一条链**——中间缺的正是那 54 条边，而它们被单独列成了 54 条互不相连的「切片」。

**最要命的一条：切片库里的东西永远变不成真切片。**

把库里的条目登记为一等切片的端点是 `POST /a/v1/slices/library/build`。实测全仓 grep（金丝雀 `fetchSliceLibrary` 命中 3 处，证明 grep 可用）：

```
library/build 命中：apps/datacore/src/app.ts:4659   ← 只有它自己的路由定义
前端调用方：0
其它 src 调用方：0
```

⇒ 属于 CLAUDE.md 铁律 0.5 三分法里的**「没接线」**（调用方集合为空，连 test 都没有）。这解释了为什么两边键的交集是 0：**库是一个永远没人按「入库」按钮的预览。**

### 2.5 实体合并层——**这是本次审查唯一一处会毁数据的缺陷**

实现（`entity-resolution.ts`）只有一条匹配规则：

```
normName(props) = String(props.name ?? props.displayName ?? props.title ?? "")
                   .toLowerCase().replace(/[\s\p{P}\p{S}]+/gu, "")
同 normName 且 ≥2 个未合并对象 → 产候选，score 恒为 1，rule 恒为「归一名称完全一致」
```

**实测扫描 Top12 有数据的类型**（`POST /a/v1/objects/merge-scan`）：

| 类型 | 对象数 | 产出候选 |
|---|---|---|
| EquipmentOEE | 5,460 | 0 |
| OrderLine | 873 | 0 |
| Equipment | 780 | 0 |
| **Process** | **650** | **5** |
| InspectionResult / Order / ProductEquipmentCapability / ExceptionEvent / ProcessCapabilityWindow / WorkOrder / WIPLot / QualityLot | 260–520 各 | 0 |

**那 5 个候选，逐个查真值——5 个全是误报，且是灾难性误报：**

| 候选 | 对象数 | 归一名 | 实际分布 |
|---|---|---|---|
| `mc_6pjr…` | **130** | 老化 | 13 个基地 / **130 条不同产线** |
| `mc_cwac…` | **130** | 化成 | 13 个基地 / 130 条不同产线 |
| `mc_97qf…` | **130** | 装配 | 13 个基地 / 130 条不同产线 |
| `mc_cza0…` | **130** | 卷绕 | 13 个基地 / 130 条不同产线 |
| `mc_4svg…` | **130** | 涂布 | 13 个基地 / 130 条不同产线 |
| **合计** | **650** | | **= 全库 Process 对象的 100%** |

这些是 130 条不同产线上各自的涂布/卷绕/装配/化成/老化**工位**，每个有自己的 `lineId`、`baseId`、`yield`、`shiftHours`、`utilization`。**它们不是同一个实体，它们是产能模型的全部节点。**

而实体合并页上，每个候选旁边就摆着「以 XXX 为准」的按钮。点一次会发生什么（读 `merge()` 实现）：

1. 129 个对象被打上 `mergedInto = golden`（此后检索/切片/聚合**只见 golden**）；
2. 所有指向被并对象的关系实例被**重指到 golden**；
3. 重指后重复的关系实例被 **`links.remove()` 物理删除**；
4. 自环（from===to）也被物理删除。

再看「还原」按钮（`unmerge()`）：它只清 `mergedInto` 标记、删除合并记录。**源码注释白纸黑字写着「links 不自动还原（审计提示）」**——第 3、4 步删掉的关系实例**不会回来**。

⇒ 按仓主自己立的判据「这道门删了，用户会不会看到坏东西？」——**会，而且是不可逆的**。一个 admin 在实体合并页点五次按钮，锂电产能模型的 650 个工序节点会塌成 5 个，关系实例被物理删除，而屏上那个「还原」按钮**不能还原它删掉的东西**。这是**阻塞级**缺陷。

同时，另一端是**召回接近 0**：实测 98 个类型里，属性含 `name` / `displayName` / `title` 的只有 **20 个**；其余 **78 个类型**的 `normName` 恒为空串，被 `if (!k) continue` 直接跳过——**永远不可能产出候选**。属于三分法里的**「接了线没数据」**（有生产调用方，但输入恒空、分支从不进入）。

**一句话**：这个模块今天的行为是「对 20% 的类型跑一条会产生 100% 误报的规则，对 80% 的类型什么都不做，且它的撤销按钮撤不干净」。

### 2.6 边界册层

`boundary/version` + `boundary/impact` 实测：3 本册、22 条常数、语义版本 `1.0.0` + 摘要指纹。

| 册 | 条数 | 消费方 | 下游 |
|---|---|---|---|
| `BASE_REGISTRY` | 13 | 3 | 4 |
| `SEG_REGISTRY` | 3 | 4 | 3 |
| `PLAN_GOAL_TARGETS` | 6 | 3 | 2 |

这一页的**机制是好的**（单一来源 + 指纹 + 影响面 + 门强制派生），但它和本体是**两套互不相识的常数体系**：13 条基地常数与 `Base` 这个对象类型的 13 个实例**是同一批基地**，却分别活在契约包和对象库里，屏上没有任何一处把它们对上。

另需点名一处 UI 纪律问题：`BoundaryPage.tsx` 把 `c.file`（源码文件路径）直接渲染在用户屏上。这与「源码文件名/行号不上用户屏」的口径冲突。

## 3. 能力 × 模块矩阵

**读法**：● = 该模块今天真提供 · ◐ = 提供一半/只读/需手工 · ○ = 不提供。
**🔁 = 重合格**（同一能力 ≥2 个模块提供，且实测口径不一致）。**❗ = 缺失格**（全行无 ●）。

#### R-9 详证（这一条我亲手跑了，不是读代码推的）

发布一个新的已发布本体版本（`OntologyVersion` 快照），今天有**三条路**：

| # | 路径 | 角色守卫 | 不变量闸 | 会签 | 谁在用 |
|---|---|---|---|---|---|
| ① | `POST /a/v1/ontology/publish-requests` → `/:id/signoff` → 全域 APPROVE 后自动 `publishVersion` | 域 owner | **有**（`assertOntologyInvariantsAllowPublish`） | **有** | 本体关系页 |
| ② | `POST /a/v1/ontology/publish` | **无**（路由体就一行 `ontology.publishVersion(ctx(req))`） | **无** | **无** | 无前端调用方 |
| ③ | `POST /a/v1/modeling/drafts/:id/publish` → `modeling.publishDraft()` | **无** | **无** | **无** | **本体建模页** |

路径 ③ 不只是"新建类型"——读 `modeling.ts` 的 `publishDraft()`：对 `MAP_TO_EXISTING` 的类型，它会**往已发布类型上追加属性、追加 `sourceBindings`**（`upsertType`），再 `upsertLinkType` 建关系边，最后**直接调 `this.ontology.publishVersion(ctx)`** 切出新快照。

**实测（真后端，非推断）**：

```
发布前：版本数 1 · 最大版本号 1 · 会签请求 0
POST /a/v1/ontology/publish  →  200，返回 version: 2
发布后：版本数 2 · 最大版本号 2 · 会签请求 0     ← 会签请求始终是 0
同时：不变量 violated=1，wouldBlock=[object_type_connected_by_structural_edge]，照样发布成功
```

`OntologyRelationsPage` 的文件头注释写得很清楚：「本页**不给**直接发布按钮，那条 `POST /a/v1/ontology/publish` 会绕开会签」——**这个纪律在那一页守住了，但它只是一页的自律，不是系统的闸。** 另外两条路照样通。

⚠ 补一条诚实位：即便走会签路 ①，那道不变量闸今天也**恒放行**——`app.ts` 的注释自陈「第三类边的闸：**今天恒放行**（产品尚未裁决『违反不变式该阻断什么』）」。这正对应本体 §8 的 `G-ONTOLOGY-INVARIANT-ENFORCEMENT-UNDECIDED`（◑ 部分闭合）。所以今天的真实状态是：**三条发布路，会签只挡得住其中一条，而不变量一条都挡不住。**

## 5. 整合方案：**七个入口 → 三个模块 + 一个下拉框**

### 5.1 设计原则（先立判据，再谈拆并）

1. **一个模块 = 一个问题。** 说不出它单独回答哪个问句的，不配当模块。
2. **同一个词只准指一个东西。** 「切片」今天指三样，必须收敛成一样；另两样改叫别的名字。
3. **参数不是模块。** 视角、着色、过滤一律降为页内控件。
4. **健康度上首屏。** 不变量报了警而要滚到页底才看得见，等于没报。
5. **不可逆动作必须先证明可逆。** 撤不干净的操作，按钮就不该在那里。

### 5.2 目标形态

```
导航组「本体」（3 项，替换今天的「建模与图谱」11 项 + 「图谱体系」8 项）

┌─ ① 本体总览 ───────────────────────────────────────────────────┐
│  答：这套本体今天健不健康、缺在哪、我该先修哪一条              │

│  · 体检条：8 条守卫 7 过 1 违 → 22 个孤立类型可点开逐个处理     │
│  · 覆盖条：80.4% 的对象不在任何业务切片上 → 可点开看是哪些      │
│  · 数据条：87/98 类型有实例，11 个空                            │
│  收编：ontology-relations 的体检段 · object-types · domains     │
│        · interfaces · 今天没有的「健康总览」                     │

│  · 只有一批数据（不再有「注册的」和「库里的」两批）            │
│  · 三档：已发布契约 / 草稿 / 候选（候选 = 今天切片库那 61 条，  │
│    一键「采纳」即调 library/build 变成草稿 —— 这就是 A 类接线） │
```

### 5.3 每条并法的理由（不是为了少几个菜单项）

| 并法 | 理由 |
|---|---|
| 图谱 9 入口 → 1 个视角下拉 | 它们本来就是同一个组件同一个端点的 8 组参数（§1 已证）。这不是「合并功能」，是**把参数从导航层放回它该在的控件层** |
| 图 + 表并成一个编辑器 | 今天的割裂是**技术性的**：图谱边不带 `linkKey`（实测 0/118），所以点不动。补上 key 之后，「看」和「改」就没有理由分成两页 |
| 切片 + 切片库并成「取数契约」 | 两边键交集 0 是**症状**，病因是「库里的东西没有入库通道」。补上通道（A 类接线，端点已存在）之后，两者天然是同一批数据的两个成熟度档位 |
| 95 条 coverage 改名降级 | 它们不回答「取哪些数」，只回答「这个类型有多少对象」。放在取数契约里会**把 4 条真契约淹掉 24 倍**——这正是仓主「看不到重点」的来源 |
| 体检提到总览首屏 | 8 条守卫已经在报 22 个孤立类型，`blocking=false` 且位置在页底 ⇒ 报了等于没报 |
| 实体合并移出本体组 | 它处理的是**实例**层的重复记录，不是**类型**层的建模。放在本体组里，会让人以为「合并」是本体操作 |
| 边界册移出本体组 | 它管的是 22 条业务常数的单一来源，与 98 个对象类型是正交的两件事 |

### 5.4 不动的东西（明确划界，防止整合变成重写）

- `SliceInspector` / `SliceLayersPanel` 两个组件**照原样复用**，它们已经是两页共享的正确形态；
- 十六层投影（`slices/:key/layers`）**不动**，直接挂到取数契约的详情里；
- 空图诊断 `diagnoseEmptyGraph` **不动**，只需让另一条 resolve 路也用它；
- 边界册的**机制**（单一来源 + 指纹 + 门强制派生）**不动**，只搬位置 + 去掉屏上的源码路径；
- 血缘链路 **不动**，只补入口。

## 6. 对照企业级标准的差距（按锂电制造 + 经营决策推演裁剪，不照搬清单）

我按做过的几套大型制造业本体落地的验收清单逐条对，并**明确标出这套系统可以不要的**——照搬清单是顾问式浪费，不是工程。

### 6.1 这个业务**真正需要**、而这套系统**没有**的

| # | 能力 | 为什么这个业务需要 | 今天的状态 |
|---|---|---|---|
| **E-1** | **多属性 + 分块的记录归一** | 锂电制造的主数据重复是真问题：同一家供应商在 ERP / SRM / 采购台账三处不同写法；同一个物料在 BOM 与库存两处编码不同。但**「名字一样」在制造业恰恰是最弱的信号**——130 条产线上都有「涂布」 | 只有单条名称规则，实测 **100% 误报**（§2.5） |
| **E-2** | **归一的可逆性与影响面预演** | 合并会重写关系实例。产能模型的关系一旦被物理删除，整条推演链会静默算错——正合铁律 1.5 那个「跑得起来不等于算得对」的形态 | `unmerge` 不还原关系实例；合并前无影响面预览 |
| **E-3** | **共享属性类型（值类型注册表）** | 「产能」在这套本体里出现在 Base/Line/Process/Model 至少四类上，各写各的 `dataType`+`unit`。做经营推演时，跨类型加总口径全靠人记 | 三条候选路径全 404 |
| **E-4** | **数据质量规约（类型级）** | 推演的输入若三个月没更新，结论是错的但屏上照样有数。`EquipmentOEE` 有 5,460 条——没有新鲜度约束就没法判断它能不能进推演 | 无。`DataSourceHealth` 是对象类型不是规约 |
| **E-5** | **本体健康的单一入口** | 22 个孤立类型 + 80.4% 对象不在业务切片上 + 1 条违反的守卫，是**同一个问题的三个侧面**，今天分散在三处 | 无 |
| **E-6** | **变更提案 / 分支** | 换行业模板、加一个基地、改一条传导系数——这些是有风险的本体变更，需要「先在分支上改完看影响再合」 | 版本只有线性快照 1 个；`branches` / `proposals` 404 |
| **E-7** | **图与表打通（可点的边）** | 业务专家在图上发现「这里少一条线」，必须能当场点进去补，否则图只是海报 | 图谱边 `linkKey` **0/118** |
| **E-8** | **孤立节点的处置闭环** | 竞品价格 / 竞品份额 / 赢单丢单 / 外部信号 / 需求分段 / 决策缺口 —— 全部是经营推演的输入，全部零关系边 | 守卫报了，但 `ANNOTATE_ONLY`、位置在页底、无处置动作 |

### 6.2 这套系统**可以不要**的（明确不建议做）

| # | 常见清单项 | 为什么这个业务不需要 |
|---|---|---|
| **N-1** | 图数据库 / 图查询语言（图查询 DSL 直通用户） | 用户是经营决策者不是图工程师。**切片（root→hops 声明式）已经是更好的抽象**——它把「怎么走」变成可治理的资产而不是每次现写的查询。补充切片的覆盖面即可，不必再加一层查询语言 |
| **N-2** | 通用推理机 / 本体公理（OWL 式子类推理） | 这套本体是**决策模型**不是知识分类学。98 个类型的语义靠 42 条传导规则承载，那才是推演真正走的边。上推理机会引入一层不可解释的推导，与「推演过程必须可披露」的要求直接冲突 |
| **N-3** | 大规模众包式本体协作（多人并发编辑同一类型） | 单租户单团队规模。会签链（`publish-requests` → `signoff`）已经够，不需要冲突合并与逐字段锁 |
| **N-4** | 时序本体 / 双时态建模（valid-time + transaction-time 全量） | 已有时序域（`TsAggSpec` / 模拟时钟 / `ObjectPropHistory`）与快照版本。全量双时态的复杂度对「今天该不该扩产」这类问句没有回报 |
| **N-5** | 联邦本体 / 跨租户本体对齐 | `tenant_id everywhere` 是硬不变量（R2），跨租户一律 403/404。联邦与这条不变量正面冲突 |
| **N-6** | 自动本体学习（从数据自动生成类型） | 已有半自动建模（`modeling` 页 AI 建议草案 + 人审）。全自动会绕开会签，与 R4 冲突 |
| **N-7** | 语义检索**全量铺开** | 我把它降级而不是列进必需：98 个类型、859 个属性的规模，靠域分组 + 关键字已经够找。**只在一个位置真需要**——「我这个业务问题该用哪条取数契约」的匹配（`slices/plan` 已有 `question` 形参）。除此之外不必上向量库 |

> N-7 这一条我改过一次判断：初读时把「语义搜索 0」列为缺口，追一层发现 `embeddings.ts` 已存在且已服务知识库，而本体侧的真实痛点是**契约选择**不是**对象检索**——按痛点而不是按清单定优先级，它就从「缺口」降成了「可后补的窄用途」。

## 7. 排序：阻塞级 vs 可后补

**判据**（沿用仓主自己立的那条）：**「这条不做，用户会不会看到坏东西 / 看不懂 / 不能用？」**

### 7.1 🔴 阻塞级 —— 不做就会出事或看不懂

| 序 | 事项 | 类别 | 判据落点 | 对照实验（验收标准，照铁律 1.5） |
|---|---|---|---|---|
| **P0-1** | **停用实体合并页的一键合并** | 缺陷 | **会毁数据且不可逆**：5 个候选覆盖全部 650 个 Process 对象，合并会物理删除关系实例，`unmerge` 不还原 | 扫描 `Process` 后，页面**不得**出现可直接执行的「以 X 为准」按钮；候选必须先显示「将合并 130 个对象、影响 N 条关系、其中 M 条会被删除且不可还原」 |
| **P0-2** | **修记录归一规则** | B 类 | 名称单键在制造业必然误报 | 同一次扫描：`Process` 的误报候选数必须从 **5 → 0**；同时构造一组真重复（同 `supplierCode` 不同写法的 Supplier）必须被判出——**两个数缺一个都不算交付** |
| **P0-3** | **图谱边补 `linkKey`** | A 类（补字段）+ 整合 | 图与表今天无法互跳，是「重合又对不上」的技术根因 | 图上任取一条边，能跳到关系编辑表单并命中同一条记录；且 `flow` 边数与关系注册表数**必须相等**（今天 118 vs 114，差的 4 条 metric 伪节点边要么归类要么剔除） |
| **P0-4** | **本体健康上首屏** | A 类接线 | 8 条守卫已在报 22 个孤立类型，位置在页底 + `blocking=false` ⇒ 等于没报 | 进入本体总览首屏即见「7 过 1 违 · 22 个类型无关系」；点击可列出全部 22 个并逐个跳到编辑器 |

## 9. 一页纸小结（给仓主）

**你看不懂它们的关系，是对的——它们不是同一种东西。** 七个「模块」里，两个是导航分组（其中一个把另外四个装在里面），五个是页面，而「图谱体系」那 8 项其实是同一张图的 8 组参数。

**功能重合，有九处，最重的三处**：9 个入口通向同一张图；「切片」一个词指三样互不相交的东西（99 条 / 61 条 / 54 条边）；结构边有 114 / 118 / 54 三个对不上的口径，且图上的边不带 key，点不动。

**缺的内容，要分两类看**：
- 一类是**后端已经有、前端没露出来**（切片库的入库按钮、合并的逐字段存活、空图诊断、体检的 8 条守卫、实例级血缘到源行、变更影响预览）——这些是接线工作，小时级；
- 一类是**系统里压根没有**（共享属性类型、数据质量规约、本体分支、本体健康总览、能用的记录归一）——这些是设计 + 实现，周级。

**最要紧的两条，都和整合无关**：

1. **实体合并页会毁数据。** 现在扫一次 `Process`，会给出 5 个「候选」，每个 130 个对象，加起来正好是全库 650 个 Process 的**全部**。它们是 130 条产线上各自的涂布/卷绕/装配/化成/老化工位，**不是同一个实体**。点一下「以 X 为准」，产能模型会塌，关系实例被物理删除，而旁边那个「还原」按钮撤不回来。**建议先停用，再修规则。**

2. **本体发布有三条路，会签只挡得住一条。** 我亲手跑了：直接打发布接口，已发布本体版本从 1 变成 2，会签请求全程是 0，而那条正在违反的不变量（22 个孤立类型）一次都没拦。本体建模页的「发布」也走这条不过会签的路，且它会**往已发布的类型上追加属性**。这是 R4（真值写入经审批）在本体域的实际豁口。

**整合方案是 7 → 3**：本体总览（健不健康）· 本体编辑器（关系是什么、改了波及谁、怎么发布）· 取数契约（业务问题取哪些数）。实体合并归数据接入、边界册归平台治理——它们本来就不是本体建模。

**明确不做的 6 项**也写在文里（图查询语言、通用推理机、众包协作、全量双时态、联邦本体、全自动本体学习），理由逐条给了——不照搬清单是这份方案能落地的前提。
