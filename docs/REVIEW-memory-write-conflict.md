| 项 | 值 |
|---|---|
| 性质 | 外部文章评审意见（非平台 PRD 增量；§5 给出与平台 PRD 的对照与分歧裁决建议） |
| 评审对象 | 多 Agent 共享记忆写冲突文章（DAG 系列第三篇，对应 ontology-engine-demo/phase4） |
| 结论 | 框架正确（预防层+处理层+读写一致三段式）；存在 1 个概念级缺陷、19 项机制级缺口、3 项更优解遗漏、1 项验证缺失，按下文补充后方可作为实现依据 |

## 1. 概念级（最高优先）：必须先划清"记忆 ≠ 真值"的边界

文章将 RULE 层同时当作 Agent 共享记忆与规则真值库，且置信度仲裁可自动 deprecate 旧规则——**等于允许 Agent 绕过审批直改企业规则真值**。"认证阈值 30→15 天"是业务决策，0.9 的置信度不构成变更授权。需补充：

1. 四层记忆（CRITICAL/RULE/CONTEXT/BACKGROUND）逐层声明：authoritative（权威真值）/ derived（派生缓存）/ ephemeral（过程记忆），以及各层的合法写入者与写路径；
2. 正确形态：**Agent 只写"提案"，真值变更只经审批流进入版本化规则库**。确立此边界后，文中大半"写冲突"退化为"提案并存"——并存提案无需仲裁删除，审批时人看到全部候选即可。文章的 workspace 隔离（写 `rule_proposals/`）已暗合此意但未说破，导致与"置信度自动 deprecate"自相矛盾；
3. 置信度仲裁的用途重新定位：用于**检索排序与提案排序**，不用于自动裁决真值。

## 2. 机制级缺口（19 项，按方案分组）

### 写锁（5 项）
1. `threading.Lock` 为进程内锁，多实例水平部署下整段失效——需补分布式锁选型（PG advisory lock / Redis SETNX+TTL）与单机适用边界声明；
2. 锁 TTL 与持有者崩溃回收（A 持锁挂死 → B 永久阻塞）；
3. **Fencing token**：锁过期后原持有者"复活"携旧上下文写入——需单调令牌拒绝过期写者；
4. 锁粒度矛盾：层级整锁串行全层，但文章自证"不同规则 ID 不冲突"——锁应为 rule_id 粒度；
5. 跨层事务（一次提案写 RULE+CONTEXT 两层=两把锁）的锁排序约定（死锁预防）。

### 乐观锁（2 项）
6. 重试缺退避与上限；且缺语义判断——重读后发现对方已写入同语义内容时应放弃而非再写；
7. 并发 insert 同 key 的唯一约束冲突路径未覆盖（update 有版本号，insert 没有）。

### 置信度仲裁（4 项）
8. **置信度计算与校准公式缺失**：Agent 类型/验证状态/历史准确率如何量化为分值？LLM 自报置信度系统性过度自信，未经校准（如历史采纳率回归）的 0.9 vs 0.7 比较是伪精度；含新 Agent 冷启动默认值；
9. 平局带宽：0.90 vs 0.89 谁赢？建议差距 <0.1 一律进人审；
10. 仲裁审计与回滚：deprecate 由谁裁、依据、能否撤销；
11. `requires_human_review` 之后的人工仲裁流程（队列/角色/SLA/超时默认）断在半空。

### 工作区隔离（2 项）
12. **Router 合并算法整体缺失**（方案最难的 20%）：同规则不同字段的 field-level merge、语义冲突（A 调阈值 vs B 停用整条）、三方合并的 base 版本、合并失败回退；
13. 工作区生命周期：任务崩溃后的孤儿 workspace 清理。

### 快照隔离（3 项）
14. **实现自相矛盾**：方案二的 `UPDATE content` 原地覆盖旧版本，`created_at <= snapshot_time` 拿不回 T2 时刻内容——快照隔离前提是**不可变多版本存储**（append-only），存储模型必须改；同理 deprecated 过滤需按 `deprecated_at > snapshot_time` 判断，否则"T2 时还活着"的记忆被错误排除；
15. **写偏斜（write skew）**：A、B 各基于快照检查约束后同时写入、合计违反——需提交时约束重验；
16. 多版本垃圾回收/保留期。

### 通用（3 项）
17. **幂等键**：重试场景先去重再谈冲突；
18. 冲突处理结果的可观测性：冲突率/锁等待时长/仲裁结果分布指标——"冲突概率 <5%" 当前是断言不是数据；
19. 存储选型边界：SQLite 单写者与 PG 行级锁对各方案适用性的影响。

## 3. 遗漏的更优解（至少应作对比出现）

20. **取消优于仲裁**：情况二（v2 未完、v3 启动）最佳解是 v3 启动时**主动取消 v2**（generation/lease 机制，旧代次写入直接被拒）——把冲突消灭在调度层，而非让两版本跑完再仲裁；
21. **事件溯源**作为根治路径：append-only 事件日志 + 物化视图，天然无覆盖写；
22. 队列化单写者（per-key serialized writer）作为锁的替代形态。

## 4. 验证级

23. 补冲突率度量与压测方法——乐观/悲观选型依据须来自数据（文章自己给出的 10% 分界线无法被验证）。
