## 一、核心方法：**四分类判据**（本单的灵魂，别跳过）

屏幕上每一个数字/结论，必须落进且只落进以下四类之一。**不许写"看起来正常"**——那不是一个类别。

| 类别 | 判据（必须用**变异**证明，不能靠读代码下结论） | 记法 |
|---|---|---|
| **A 真算** | 改变一个上游输入 → 该数字**跟着变**，且变化方向/量级说得通 | `A` |
| **B mock** | 数字来自 `mocks/`（MSW handler 或 fixtures），真实部署下会变成另一个值或空 | `B` |
| **C 写死** | 改变**任何**上游输入，该数字**纹丝不动** | `C` |
| **D 静默降级** | 上游缺数/报错，但界面呈现得像正常结果（无灰、无标注、无错误码） | `D` |

**判定手法（强制）**：对每一个数字，**至少做一次变异**——改一个杠杆、换一个基地、改一个 seed、或直接在后端把该字段的计算改成常量——然后看屏幕。

- 屏幕跟着变 → A
- 屏幕不变 → C（或该输入根本没接上，同样记 C 并注明"输入未接"）
- 断网/停 datacore 后屏幕仍有数 → B 或 D，再区分

> ⚠️ **本项目血泪**：只读代码得出的"它是真算的"结论，本会话已经错过至少三次。**必须亲手变异**。

## 二、前后端**双侧对拍**（不是"分别测"，是"同一入参两边比"）

这是本单区别于普通 UI 测试的关键。每一条断言都要有两侧证据：

```
①  前端侧：浏览器里操作 → 记下屏幕上的数字（截图 + 文字）
②  后端侧：用**同一组入参**直接调求解器 → 记下返回值
③  比对：两边应当能对上（相等，或前端做了可解释的格式化/聚合）
```

后端直调方式（二选一，都要显式捕获退出码）：

```bash
# 方式一：起内存态 datacore，用 HTTP 直调（推荐，最接近真实链路）
PORT=4001 JWT_SECRET=dev BLOB_DIR=/tmp/blobs SEED_DEMO=1 CREDENTIAL_KEY=<64hex> \
  node apps/datacore/dist/server.js &
curl -sS -X POST localhost:4001/a/v1/solvers/risk_timeline/invoke \
  -H 'X-Debug-User: demo:u1:admin' -H 'content-type: application/json' \
  -d '{"args":{"baseId":"changzhou","windowDays":30}}' | jq .

# 方式二：在 datacore 测试里直接 invokeSolver（见 apps/datacore/test/helpers.ts）
```

**对不上就是发现**。对得上也要记录——那是 A 类的证据。

> **注意口径陷阱**：前端可能做了聚合/取整/换算。对不上时先确认是"口径差"还是"值错了"，两者都要写进台账，但只有后者是 bug。

## 三、LOOP 协议（每轮五步，循环到退出条件）

**第 N 轮：**

1. **穷举操作**（不许抽样）：按下面的控件台账，把本轮范围内每个控件点一遍。每次点击后**等待加载完成**再取证——本项目有把 loading 渲染成失败态的前科。
2. **逐数取证**：对屏幕上出现的每个数字/结论，做一次变异，判 A/B/C/D，填台账。
3. **双侧对拍**：对判为 A 的，做一次后端直调比对；对不上则降级为待查。
4. **每个非 A 发现 → 写一条测试**：断言必须是**效果层**（"结果因此不同"），不是运输层（"参数到达了"）。写完立刻做**变异反证**：把实现改回坏的，确认测试变红；还原确认变绿。**两次输出都要贴进报告。**
5. **回归 + 记账**：跑相关包测试，记录本轮新增发现数。

**退出条件**：连续 **2 轮**新增发现为 0。（不是"我觉得测完了"。）

## 四、控件台账（**穷举清单**·每一行都要有结论）

按此表逐行填，缺一行即未完成。表格模板：

| # | 控件/元素 | 操作 | 屏幕结果 | 变异手法 | 屏幕是否变 | 分类 | 后端直调值 | 对得上？ | 结论/发现 |
|---|---|---|---|---|---|---|---|---|---|

**必须覆盖的控件清单（至少这些，发现更多请补进去）：**

**① 基地卡片区**
- 每一张基地卡片（**逐张点，不许只点一张**）
- 卡片上的：峰值张力数字、主因子标签、`dataMode`（实测/估算）标记、越线日
- 切换基地后：下方所有面板是否**真的跟着换**（本项目有"点基地曲线不变"的前科 → §8 G-10 相关条目）

**② 因子 chip / 作用域切换**
- 「全部因子（基地级）」
- 每一个「按 XX 细分」chip（瓶颈工序 / 设备OEE / 人力工时 / 物料齐套 / 物流时长 / 换型损失 / 良率波动）
- 切 chip 后根因树、时序全景是否**真的按该因子重算**

**③ 时序全景（30 天点阵）**
- 悬停任意一天 → 当日详情
- **每一行的颜色序列**（见下方红咬 R1）
- 「张力 X/100 → 张力 Y/100」的起点与终点
- 「T+N 越线」/「窗口内不越线」判定

**④ 根因推演树**
- 树是否出现（vs 诚实灰）
- 每一个节点的展开/收起
- 叶级下钻 → 是否落到**真对象**（订单号/设备号可查）
- 诚实灰出现时：它给的病因**是否与真实失败原因一致**（见红咬 R2）

**⑤ what-if 杠杆区**
- 每一个滑杆（逐个拖，记下拖前拖后的值）
- 拖动后：结论、处置计划表、时序全景是否**实时联动**
- 「重算」/「行动计划」按钮

**⑥ 处置计划表**
- 每一行行动项：能否点开详情
- 每一行的数字是否带单位
- 调整杠杆后：行动项内容是否**真的变**（本项目前科：写死不变 → 已修，本轮复验是否复发）

**⑦ 受影响订单 / 下钻**
- 订单列表是否为空（前科：没有一天有影响订单）
- 点订单 → 是否可达详情

**⑧ 空态与错误态**
- 断开 datacore → 每个面板的表现（应当是诚实灰 + **真实**错误码，不是伪造病因，不是静默 0）
- 选一个没有数据的基地 → 表现

## 五、已知种子红咬（**开工前先复现这几条**，它们是本单的验收锚）

> 这些是用户与审核方已实际观察到的症状。**逐条复现 → 定性 → 修 → 写测试 → 变异反证**。若你复现不出来，说明环境不对（先查是不是部署镜像陈旧），不要直接判"已修复"。

**R1 · 所有基地的瓶颈都一样**（用户亲报，本单最高优先）
- 复现：逐个点基地卡片，记录每个基地的"主因子/瓶颈"。
- 期望：不同基地的产线配置/订单结构不同 → 瓶颈**不应**全相同。
- 若全相同：查 `primaryFactor()` 是否真吃 baseId、还是取了全局最大；查各基地的因子张力是否真的按基地算。
- 断言：至少两个基地的 `primary` 不同（若数据上确实应该相同，**必须给出可核查的理由**并把该理由写进测试注释）。

**R2 · 时序全景 30 点一色 · 三因子张力终点同为 98**（用户第三次提）
- 复现：看信阳/扬州的全景图。观察到：瓶颈工序 91→98、物流时长 92→98、设备OEE 84→98，**三个不同因子不同起点，终点全是 98**；且每行 30 个点同色。
- 怀疑：① `98` 是硬上限被 clamp；② 所谓"时序"其实是静态阈值分桶，没有逐日演化。
- 断言：同一因子在不同日的 tightness **不得恒等**；三个不同因子**不得同落一个值**（除非给出可核查理由）。

**R3 · 诚实灰面板伪造病因**（`RiskBoardView.tsx:869-877`）
- 现状：`loading` 与 `error`/无数据共用同一空态块 → 请求还在飞就宣告"暂不可用"；且第 877 行「补齐路径：仅缺引擎侧作用域」**无条件渲染**，不分支。
- 而该诊断**已过期**：本体 §8 记载 `G-GAP-SCOPE` 早闭，同症状真因是后端镜像陈旧未 rebuild。
- 断言：loading 态必须渲染加载中（不得出现"暂不可用"字样）；病因文案只陈述**可观测事实**（HTTP 状态/错误码/空返回），不得内联因果推断。

**R4 · `base_capacity_outlook` 未走 base 归一 → 硬 404**（`solvers/service.ts` `baseCapacityOutlook`）
- 现状：`str(args.baseId)` 只认 `baseId` 与中文名，**不认真实对象 id `obj_base_<id>`**；而地图页选中写入的就是该形态。兄弟求解器 `risk.ts` 已走 `normalizeBaseRef`。
- 断言：同一基地三种形态（`obj_base_xxx` / `xxx` / 中文名）结果一致。

**R5 · 前端把 mock 形态 id 写进 selectedObjects**
- `RiskBoardView.tsx:230` 用 `base-${card.base}`（中文名），真实 id 是 `obj_base_changzhou`；而 `mocks/fixtures.ts:59` 恰好是 `base-${b.name}` → **前端测试为错误形态背书**。
- 症状：点风险卡（视觉已选中）→ 问"受影响订单"→ 系统反问"请提供基地"。
- 断言：写入 `selectedObjects` 的 objectId 必须来自后端返回的真 id；并把 fixture 的 id 形态与真实态对齐。

**R6 · what-if 杠杆写死**（§8 `G-WHATIF-HARDCODED-LEVERS`）
- 复现：拖每一个滑杆，看结论/计划表是否真变。

**R7 · 受影响订单恒空**（用户曾报"没有一天有影响订单"）
- 复现：逐日悬停，看是否任意一天有订单。

**R8 · 裸数字**（§8 `G-UNIT-NORMALIZE`）
- 本页每一个数字都要有单位/量纲。发现裸的：**先查后端/契约有没有 `unit` 可消费**，有就消费，没有才就近标注并说明原因。

## 七、反假绿纪律（**本项目真出过事故，逐条遵守**）

1. **退出码必须显式捕获**。禁止 `cmd | tail -n; echo "EXIT=$?"` —— `$?` 取的是管道末端 `tail` 的退出码（恒 0）。本项目曾据此把一个**编译失败**的 commit 判为"BUILD 通过"并入正线。一律用 `out="$(cmd 2>&1)"; rc=$?`。
2. **vitest 不做类型检查**：`TEST` 绿 ≠ 能编译。必须另跑 `npx tsc -p <pkg>/tsconfig.json --noEmit` 并看真退出码。
3. **测试写得像有牙 ≠ 真有牙**：每条新断言都要做变异反证（改坏→红，还原→绿），把两次输出贴出来。
4. **fixture 不许自造契约里没有的字段**：`as SomeType` 强转 + 自造字段 = 测试自产自销。本项目已因此让一个功能死了半天没人发现。
5. **运输层断言不算接缝测试**：断言"参数到达了"没用，要断言"结果因此不同"。
6. **"进程还在" ≠ "还活着"**：判断长任务是否卡死，看 CPU 占用 + 日志写入时间戳 + worker 是否存在，不看进程表里有没有那一行。
7. **别信任何"看起来正常"**：本页历史上多次出现"绿测试 + 界面正常 + 数是错的"。
