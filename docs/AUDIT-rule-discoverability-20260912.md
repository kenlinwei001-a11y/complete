### 3.1 但「没有 description」不等于「规则完全没有可检索文本」——必须说清

`apps/agentcore/src/dril/resource-projector.ts:170 projectRules()` 有兜底：

```ts
description:
  nonEmpty(r.description, r.name && r.name !== r.key ? r.name : undefined, `合规规则 ${r.key}`) ?? `合规规则 ${r.key}`,
...
expressionSummary: nonEmpty(r.expression),
```

⇒ 规则进检索索引时 `description` **回落成它的 `name`**（如「外协比例红线」），并另带 `expressionSummary`。
**所以规则不是「零文本」，是「只有一个 4–8 字的名字 + 一条 DSL 表达式」。**

**而同一个文件里，切片那一路是这么写的**（`:158-159`）：

```ts
...(s.answersQuestions && s.answersQuestions.length > 0 ? { answersQuestions: s.answersQuestions } : {}),
...(s.tags && s.tags.length > 0 ? { tags: s.tags } : {}),
```

**规则那一路没有这两行。** 即便哪天有人给规则填了 `tags`/`answersQuestions`，
**`projectRules` 也不会把它们投出去** —— 这是「接了线接错地方」那一档，不是「没数据」那一档。
**两者修法不同**：前者要改投影函数，后者只要补种子。**这条是本单最容易被误报的一处**，单独标出。

### 4.2 为什么 **C 档（排不进 top-6）实测为 0** —— 派单的 `MAX_SOLVERS = 6` 担忧不落在规则上

派单担心「`MAX_SOLVERS = 6` 把上游夹死 ⇒ 带它的求解器排不进 top-6 ⇒ 实际不可达」。
**追到读取点后这条不成立，理由是规则根本不走那条路**：

`MAX_SOLVERS` 只截断 `navigation-slice.ts` 投影给模型的**提示文本**里列几个求解器（`:528`）。
而规则进入模型视野靠的是**求解器真被调用之后**的 `evaluatedRules` 回包
（`apps/datacore/src/solvers/service.ts:6543 evaluateRuleRefs`）—— 那是**执行期**，与「提示里列了几个」无关。

**判据**：一次 `invoke_solver("carbon_footprint")` 无论 `carbon_footprint` 在导航图里排第几、
甚至**根本没被列出来**，只要模型调了它，`SOLVER_RULE_REFS["carbon_footprint"] = ["C33"]` 就会被逐条求值并回带。
⇒ **截断影响「模型容易不容易想到调它」，不影响「调了之后规则出不出来」。**
这是两个不同的量，不该合成一句。

故 26 条的可达性**不由 top-6 决定**，C 档无实例。**真正的门槛在别处**（§5.2 的工具说明、§6 的根因）。

```ts
const bindings = this.objectConstraintBindings(c, solverKey);   // ← 第二来源：对象类型上挂的约束
const declared = SOLVER_RULE_REFS[solverKey] ?? [];             // ← 第一来源：编译期常量表
const refs = [...declared, ...[...bindingOf.keys()].filter((k) => !declared.includes(k))];
```

第二来源是**运行期数据**（管理员可在界面上给对象类型挂 `constraintRefs`，`datacore.ts:224` 外键校验）。
⇒ **只查 `SOLVER_RULE_REFS` 就断言「C34 没人评估」是不够的** —— 必须把这一路也量掉。

**实测**（真起服务·`GET /a/v1/ontology/object-types`）：

```
对象类型数 = 100
金丝雀 Base 在? true | Order 在? true        ← 探针有鉴别力
带 constraintRefs 的类型数 = 0
constraintRefs 引用的规则并集 = （空）
C34 被对象约束引用? false | C12? false | C25? false
```

**100 个对象类型，零个挂了 constraintRefs。** ⇒ 第二来源在今天的种子里**完全是空的**，
C12 / C25 / C34 的「零引用」结论成立，定性从「接了线接错地方（近似）」**收紧为「没接线」**。

> **顺带记一笔（本单范围外，但属同族）**：`WO-CONSTRAINT-REFS` 这整套机制
> —— 外键校验、payload 填空合并、规则被 retire 时诚实出 `NOT_APPLICABLE` 点名断链
> （`service.ts:6570-6578` 一大段） —— **实现齐备、注释详尽、零条种子数据**。
> 这是铁律 0.5 三分法里**「接了线没数据」**的又一例：不是机制不存在，是没人填。
> **修法是填数据，不是造机制** —— 把它报成后者会直接歪掉排期。

## 5 · 三条通路各是什么（派单的「唯一通路」前提**推翻**）

派单写：「规则**不经语义检索**进模型视野。唯一通路是 `navigation-slice.ts:545-549`。」
**追到读取点后，这句话的两半都不成立。** 实际有**三条**通路，性质各不相同：

| # | 通路 | 带的是什么 | 覆盖 | 触发条件 |
|---|---|---|---|---|
| ① | **执行通道** `SOLVER_RULE_REFS` → `evaluateRuleRefs` | 真规则 key + PASS/WARN/BLOCK | **26 / 30** | 模型**调了**对应求解器 |
| ② | **检索通道** DRIL `retrieve_knowledge` | 真规则 key + name + expression | **30 / 30 可入索引**，但真实问法实测 **5 / 20** | 模型调了 `retrieve_knowledge` **且问句复述了规则名** |
| ③ | **全量评估通道** `evaluate_rules(ALL_APPLICABLE)` | 全部 30 条 key + name | **30 / 30** | 模型主动调 `evaluate_rules` |
| — | ~~`SOLVER_RULE_HINTS`~~ | **0 条规则**（见下） | **0 / 30** | —— |

### 5.1 `SOLVER_RULE_HINTS` 带的规则数是 **0**，不是「少」

派单把它当成规则的通路。**读它的类型就知道不是**（`navigation-slice.ts:403`）：

```ts
const SOLVER_RULE_HINTS: Record<string, string> = {
  gap_attribution: "缺口勾稽：Σ子贡献 + residual == 父缺口（不勾稽即失真）",
  carbon_footprint: "碳足迹超阈值 → 欧盟碳护照不合规（VERDICT=FAIL）",
  ...
};
```

**`Record<string, string>` —— 值是 7 句手写散文，一个 `Cxx` 都不含。**
`:545-549` 那段把这 7 句塞进 `slice.rules[]`，字段名叫 `rules` 而已。

**实跑证据**（真调 `projectNavigationSlice`，6 条问句 + 金丝雀）：

```

「4680-NCM 加 20% 六周能不能接？」      rules[1] = ["承诺量 ≤ 现货+在制+交期前可排产能（不得超卖）"]   含 Cxx: 0
「4680-NCM 出口欧盟的碳足迹达标吗？」    rules[3] = [碳足迹… / 缺口勾稽… / 双向勾稽…]                含 Cxx: 0
```

**6 条问句，`rules[]` 里规则 key 总数 = 0。** 而金丝雀非空 ⇒ 这是真实结论，不是探针坏了。

⚠ **最后一条最值得看**：一个**直接问规则**的问句（还点名了 C08 的业务名「外协比例红线」），
导航图给模型的是 **`solvers[] = 空`、`rules[] = 空`**。**这张图对「问规则」这件事完全失语。**

⇒ 三分法定性：**`SOLVER_RULE_HINTS` 对规则而言是「没接线」**——它压根不是规则的通路，
是**求解器的注意事项备忘**。把它当规则通路去修（比如「给它加更多条目」）会修错东西。

### 5.2 `evaluate_rules` 的工具说明**把范围说错了**，而这是模型唯一看得到的范围声明

`apps/agentcore/src/tools/registry.ts:197`：

```ts

```

对照实测的 30 条：

| | 条数 | 明细 |
|---|---|---|
| 声明范围 `C01–C23` 内**真实存在**的 | 18 | C01–C06, C08–C13, C15, C16, C18, C21, C22, C23 |
| 声明范围内**根本不存在**的（模型可能去要） | **5** | **C07 · C14 · C17 · C19 · C20** |
| **真实存在但被说明排除在外**的 | **12** | **C24–C35**（含 C33 碳护照、C34 争用、C30 良率停线…） |

**这一句话同时干了两件坏事**：把 12 条真规则挡在模型的认知之外，又请模型去要 5 条不存在的。

**反向金丝雀实跑**（要 4 条，其中 C07 不存在）：

```
→ 返回 3 条 verdict（C33 / C34 / C35），**C07 静默消失，无错误、无警告**
```

⇒ 模型若照说明去要 C07，**得不到任何「这条不存在」的反馈**，只会看到少了一条。

### 5.3 但正因为有 ③，**B 档（任何问句都到不了）实测为空**

`apps/datacore/src/rules.ts:319`：`ALL_APPLICABLE` 走 `status === "PUBLISHED"` 全量，不做任何按求解器/按问句的收窄。

```
POST /a/v1/rules/evaluate  {"ruleIds":"ALL_APPLICABLE","payload":{}}
→ verdict 数 = 30
→ 含 C01…C35 全部 30 条；金丝雀 C34 在? true | C35 在? true
```

每条 verdict 的 `explanation` 形如 `C34 跨业务线产能争用: 通过` ⇒ **key 与业务名都进了模型上下文**。
**所以「结构性不可达」在本仓不成立**：只要模型调一次 `evaluate_rules(ALL_APPLICABLE)`，30 条全在眼前。

⚠ **但这条通路的质量很差，不能当作「问题已解决」**：上面这 30 条**全部 `passed: true`**。
空 payload 下字段解析不到，`rules.ts:337-344` 走 fail-open ⇒ **30 条一律报「通过」**。
即模型拿到的是一份**「全体通过」的假安心清单**，而不是「哪几条管你这件事」。
**能看见** ≠ **判得准**（铁律 1.5 那句「跑得起来不度量算得对」的规则版）。

## 7 · 根因陈述

### 7.1 主形态

> **「我用『这条规则在系统里有定义、有表达式、能被求值』当作『这条规则能被找到』的证据，
> 而前者并不度量后者 —— 前者度量的是**存在**，后者度量的是**可检索**，
> 两者依赖的是**完全不相交的两组字段**。」**

规则今天拥有的字段（`key` / `name` / `expression` / `severity` / `category` / `params` / `scopeObjectTypes`）
**全部服务于「求值」**：给定 payload，判它违不违规。
而「被找到」依赖的是另一组（`description` / `tags` / `answersQuestions`）—— **这一组规则侧 0/30**。
两组字段不重叠，所以**规则求值得再准，也不会因此更容易被找到**。

### 7.2 同族的三句（同一天在同一条链路上测出来的）

| # | 形态 | 实测 |
|---|---|---|
| ② | 「我用**字段名叫 `rules`** 当作『它装的是规则』的证据」 | `slice.rules[]` 装的是 7 句散文，规则 key 数 **0**（§5.1）。**派单正是被这个字段名骗到的** |
| ③ | 「我用**工具说明里写的范围**当作『那就是真实范围』的证据」 | 说明写 `C01–C23`：漏掉 12 条真规则、请模型去要 5 条不存在的（§5.2） |
| ④ | 「我用**规则码在文件里出现了多少次**当作『有多少条规则』的证据」 | 命中 134 次，真实 30 条（§2.2）—— 派单的「39」由此而来 |

### 7.3 **明确回答：规则的病与求解器的病是同一个还是两个？**

> **答：两个不同的病；求解器今天一个都没有。但两者的形态同源 —— 都源于「规则被当成求解器的附属品来登记」。**

**先给判据，再给结论**（同一棵树、同一次取证，§3）：

| | 规则 | 求解器 |
|---|---|---|
| 检索元数据 `description`/`tags`/`answersQuestions` | **0 / 30 · 0 / 30 · 0 / 30** | **63 / 63 · 63 / 63 · 63 / 63** |
| 有没有自己的一等目录端点 | ❌（`GET /a/v1/rules` 不在 agent 工具表里） | ✅ `GET /a/v1/solvers/registry` + `discover(kind=solvers)` |
| 新增一条会不会自动被评估/调用 | **❌**（`SOLVER_RULE_REFS` 手写编译期常量表） | ✅（目录即注册表） |

⇒ **求解器不害这两个病**，所以**不是同一个病**。把它们说成同一个会导出错误的修法
（「求解器也这样，所以是平台通病」⇒ 去改检索引擎；而检索引擎是好的，缺的是喂给它的文本）。

**但两个病共用一个结构**，这才是值得记下的那一句：

> **求解器是**一等公民**（有自己的目录、自己的检索元数据、自己的发现工具）；
> 规则是**二等公民**（没有自己的目录，只有一张挂在求解器名下的引用表 `SOLVER_RULE_REFS`
> ＋ 一条身份记录）。** 于是：
> - **病 1（元数据缺口）** = 二等公民没人给它写说明 → 检索召回全靠问句与其 4–8 字名字的字面重合（§5.4：100% vs 25%）
> - **病 2（手抄册）** = 二等公民靠一张手写表挂到一等公民上 → 新规则不被任何求解器评估（§6.1）

**两个病要分开修，修法不同**：病 1 补元数据（种子 + 契约 + 投影），病 2 补引用（3 行）。
**混着修会漏**：只补元数据，C12/C25/C34 仍然不被任何求解器评估；只补引用，真实问法下照样 5/20。

### 7.4 这是 A 类不是 B 类（照禁令 1 的判据自检）

> 判据：**「这笔账删了，用户会不会看到坏东西？」**

**会。** 用户问「4680-NCM 出口欧盟的碳足迹达标吗？」，`C33 碳护照前置` 是**唯一**管这件事的 BLOCK 规则，
而检索通道**一条规则都不返回**（§5.4 S20）。屏上要么不提约束，要么模型凭常识现编一条——
**两种都是用户直接看到的坏东西**。故本项属 A 类，不受禁令 1 约束。

## 8 · 修法建议（只建议，本单未实施）

### 8.0 先划掉一条：**不建议新增任何门 / 棘轮 / 基线 JSON**（禁令 3 · 冻结令）

本单能想到的最"顺手"的机制是「加一道门：规则必须有 description」。**不提**，且明确劝阻：
门系统现状 101 道 / 40,379 行已达产品源码 21%。下面三条建议**都不需要新门**。

### 8.1 规则该不该复用求解器那套发现面？—— **该，但只复用「检索元数据」那一半，不要复用「目录」那一半**

| 复用什么 | 建议 | 理由 |
|---|---|---|
| `description` / `tags` / `answersQuestions` 三个字段 | ✅ **该复用** | 它们是 DRIL 检索的**输入**，与资源是什么种类无关。规则缺的正是它们 |
| 「进同一个全量目录」（即把规则并进 `/a/v1/solvers/registry` 一类的统一目录） | ❌ **不建议** | 规则与求解器的**动作语义不同**：求解器是「调它」，规则是「用它判」。合进一个目录会让模型分不清该 `invoke_solver` 还是 `evaluate_rules`。**DRIL 已经是那个统一检索面了**（`kinds` 含 `rule`），不需要第二个 |

### 8.2 三条具体建议（按「敞口 ÷ 代价」排序）

#### 建议 1 · 给 30 条规则补 `answersQuestions` + `tags`（**最贵，但唯一能真正修好 §5.4 那个 25%**）

**这是一个三半改动，必须一个 dev 整单做**（SEAM-GATE：拆两半必漂）：

| 半 | 文件 | 今天的行为 | 应该的行为 |
|---|---|---|---|
| ① 契约 | `packages/contracts/src/datacore.ts:649` `IndustryTemplateSchema.rules` | 字段只有 `key/name/expression/scopeObjectTypes/severity/params/category/origin/version/status` —— **`description`/`tags`/`answersQuestions` 一个都没有** | 加 3 个可选字段（加性，向后兼容） |
| ② 种子 | `apps/datacore/src/synthetic/battery.ts:737` `BATTERY_RULES` | 30 条各只有名字 | 每条补 2–4 条样例问句 + 标签 |
| ③ 投影 | `apps/agentcore/src/dril/resource-projector.ts:170` `projectRules` | **即便①②做完了也投不出去** —— 该函数没有切片那两行 `...(s.answersQuestions ? {...})`（对比 `:158-159`） | 补上两行 |

> ⚠ **③ 是最容易漏的一半**，漏了会得到「填了没反应」这个最难查的症状 ——
> 契约绿、种子绿、四包 typecheck 全绿，而检索行为**逐字节不变**。
> **验收必须用对照实验，不能用「跑得起来」**（铁律 1.5 判据一）。

**现成的验收判据（本单已跑通，可直接复用为该单的对照实验）**：

> 跑 §5.4 那两臂。**修前 臂A 30/30 · 臂B 5/20。修后要求：臂A 保持 30/30（不许回退），臂B ≥ 15/20。**
> **两个数缺一个都不算交付** —— 只报臂 B 变好，可能是把规则的召回阈值调松了，代价是臂 A 的精度。

**代价**：30 条 × 2–4 条问句 ≈ 90 句业务文案，**这是真正的成本，且必须懂电池业务的人写**，
不是改代码的成本。③ 是 2 行，① 是 3 行。

**风险（必须一起测，否则会换一个病）**：
DRIL 默认 `maxResults = 8`。30 条规则一旦有了丰富文本，**会挤占求解器的名次**。
§5.4 臂 B 里 S01「4680-NCM 加 20% 六周能不能接？」今天返回 3 个 intent + 1 个 field，
**本来就没给 solver 留几个位**。⇒ **验收时必须同时回归「求解器还排不排得进前 8」**，
否则修好了规则召回、弄坏了求解器选型 —— 那是更贵的回归。

#### 建议 2 · 改 `evaluate_rules` 的 `descriptionForLLM`（**1 行，零风险，敞口不小**）

`apps/agentcore/src/tools/registry.ts:197` 的 `（C01–C23）` 是**错的**（§5.2）。
**不建议改成「C01–C35」**——那会在下一条规则发布时立刻再次过期，是同一个手抄册病的新副本。
建议改成**不写死范围**，例如：「规则清单用 `retrieve_knowledge(kinds=['rule'])` 取；
不指定则用 `ALL_APPLICABLE` 全量评估。」

> **形态自检**：写死范围 = 「用一个会漂的常量当作真实集合的证据」。
> 本文件 §2 那条「行号会漂，写死行号的引用天生带保质期」是同一句话的另一个实例。

#### 建议 3 · 给 C12 / C25 / C34 各补一条求解器引用（**3 行，修病 2**）

`packages/contracts/src/datacore.ts:240` `SOLVER_RULE_REFS`：

| 规则 | 建议挂到 | 依据 |
|---|---|---|
| C12 预测偏差触发重校 | 需求/预测族求解器 | 其 `scopeObjectTypes=["Model"]`、`category=需求` |
| C25 外部终端需求假设偏离 | 同上 | `scopeObjectTypes=["ExternalSignal"]` |
| C34 跨业务线产能争用 | 产能/争用族求解器 | 它是**为此专门新建**的多主体谓词（`battery.ts:806-820`） |

> ⚠ **具体挂哪个 solver 我不下结论** —— 这要看该求解器的 payload 里**有没有这条规则表达式要的字段**
> （`evaluateRuleRefs` 取不到字段会诚实出 `NOT_APPLICABLE`，硬挂只会多一条「不适用」的噪声）。
> **挂之前必须逐条实测字段可解析**，这正是 §5.3 那个「30 条全报通过」的假绿在警告的事。
> ⛔ **C35 不要挂** —— 它是参数载体，不是判定规则（§4.3）。

### 8.3 不建议做的两件事

1. **⛔ 不要给 `SOLVER_RULE_HINTS` 加条目来"修规则可发现性"。** 它是求解器的注意事项备忘、
   `Record<string,string>`，与规则库无引用关系（§5.1）。往里加 30 句散文 = 造**第 31…60 份**
   与规则库并存、谁也不校验谁的副本 —— 这正是本仓 `RULE_PARAM_BINDINGS` 注释里反复点名的**「诱饵」形态**。
2. **⛔ 不要靠 `evaluate_rules(ALL_APPLICABLE)` 来"解决"可发现性。** 它确实能让 30 条全进模型视野（§5.3），
   但空 payload 下 **30 条全报「通过」**。把「能看见」当成「已解决」，会造出一份**假安心清单**。

## 9 · 《我可能错在哪》（≤3 条）

1. **「真实问句」我用的是场景卡的 20 条 `triggerQuestion`，这是个有出处但不中立的样本。**
   它们是本仓自己写的、且**写卡的人同时也决定了那张卡挂哪几条规则**，所以「该出哪几条」这个标准答案
   与问句同源。若换成真实用户日志，臂 B 的 25% 可能更低（用户措辞更随意），也可能更高（用户更常直接问「有什么规定」）。
   **我能保证的是臂 A 与臂 B 的对比是有效的**（同一索引、同一端点、同一时刻），
   **不能保证 25% 这个绝对值可外推**。

2. **我没有真跑一次完整的 agent 会话（路径 B 循环），只跑到了它的两个输入面。**
   我实测的是 `projectNavigationSlice`（注入 prompt 的那张图）与 `POST /b/v1/resources/search`（DRIL 检索），
   都是模型**看到什么**；我**没有**驱动一次真 LLM 循环去看**模型实际会不会调** `evaluate_rules` / `retrieve_knowledge`。
   本仓 LLM 一律 mock，这条链要真验需要接真供应商。
   ⇒ 凡涉及「模型会不会主动调某工具」的推断（§5.2 第 2 点、§8.2 建议 2 的收益），
   **是基于工具说明文本的推断，不是实测**。我已尽量把这两类分开写，但可能有漏。

3. **臂 A 的「30/30」可能夸大了检索通道的健康度。**
   臂 A 的问句就是规则的 `name` **一字不差**，而 DRIL 无 embedder 时退化为**词法重叠比**
   （`search-engine.ts:170` 注释：「无 embedder → 词法重叠比」）。
   **完全相同的字符串必然拿满分**，所以 30/30 更像是「探针有鉴别力」的金丝雀，
   **不构成「检索引擎语义能力强」的证据**。真正承载结论的是臂 B 的 5/20 与两臂之**差**，
   我在 §5.4 是这么用的，但读者可能把 30/30 读成好消息 —— 它不是。
