## §0 · 一句话结论

> **七个模块今天铺成 20 个导航目的地，实测只承载 5 类不同的用户问题。**
> 看不懂三者关系不是文案问题 —— 是**页面边界按「数据结构」切，而用户按「问题」找**。
>
> 三个最硬的重合（都不是"相似"，是**同一份实现挂了两次**或**同一张图挂了多次**）：
> **① 9 条图谱导航 → 实测只画出 5 张不同的图**（4 条指向同一张、另 2 条指向同一张）；
> **② 两个切片页共用同一个子图面板、同一个规划器**，而它们的切片集合**交集为 0**；
> **③「本体关系」一页装着 5 件互不相干的事**（23,973 字 / 165 行）。
>
> **我的方案：20 个目的地 → 5 个页面 + 1 个画布视角切换器。**

### 2.1 重合①：两个切片页是**两批不相干的切片 + 同一份实现**

```
注册表 GET /a/v1/ontology/slices → 99 条（键 enterprise_360 / coverage_*）
派生库 GET /a/v1/slices/library  → 61 条（返回体 {intra:7, cross:54}，键 biz.*）
两边 sliceKey 交集 = 0
金丝雀：注册表里确实有 enterprise_360 = true；库里 biz. 前缀 = 61 ⇒ 比对没坏
```

而**代码就是同一份**：

```
SlicesPage.tsx        import { …, planSlice, … } + import SliceInspector from "./SliceInspector"
SliceLibraryPage.tsx  import { fetchSliceLibrary, planSlice } + import SliceInspector from "./SliceInspector"
```

⇒ 同一个规划器有**两个入口**（〔＋新建切片〕/〔规划〕页签），同一个子图面板挂**两次**。
**「切片库」这个名字让人以为它是「本体切片」的目录或子集 —— 实测交集为 0，是两个平行世界。**
更反直觉：名字听起来次要的那个，61 条**全都有真 `paths`**；
名字听起来主要的那个，99 条里 **95 条 `paths:[]` / `hops:0`**。

### 2.2 重合②：「本体关系」不是一个页面，是五个

实测 5 个分区标题逐字：`结构边 · 关系类型` / `因果边 · 传导规则` / `不变式 · 体检守卫` /
`对象类型 · 弃用流程` / `发布会签（R4）`；**165 行表格**，是另外两页之和的 4.5 倍。
它与另外两模块「看起来不相干」，**3/5 的内容确实不相干**。

### 2.3 重合③（本轮最大发现）：**9 条图谱导航只画出 5 张图**

方法：逐个渲染后取 SVG 的 `circle/rect/path/line/text` 的**几何 + 着色 + 文本**做 sha256。
5s 与 9s 两种等待各跑一遍，**结果逐字节稳定**（排除渲染竞态）：

| 导航条目 | 图元 | 图的指纹 | 屏上承诺的差别 |
|---|---:|---|---|
| 本体图谱 `graph` | 375 | `9360a84f` | 对象本体层 |
| 图谱·全景 `graph-all` | 375 | **`9360a84f` 同上** | 「+ 求解器 + 智能体一张图」 |
| 图谱·主干分级 `graph-backbone` | 375 | **`9360a84f` 同上** | 「一级/二级/三级分层」 |
| 图谱·MVP `graph-mvp` | 375 | **`9360a84f` 同上** | 「**实色高亮** MVP 核心闭环，⊕ 虚线节点」 |
| 图谱·产能推演网络 `graph-flow` | 359 | `63c8814e` | 产能金字塔 |
| 图谱·数据来源 `graph-source` | 375 | `82612063` | 「按源系统**重新着色**」 |
| 图谱·求解器 `graph-solver` | 240 | `59f86814` | 求解器绑定 |
| 图谱·学习闭环 `graph-loop` | 240 | **`59f86814` 同上** | 「预测↔实际偏差→校准器→写回」 |
| 图谱·智能体网络 `graph-agent` | 236 | `cb3505b9` | 智能体团队 |

> **金丝雀内建**：这把哈希器产出了 **5 个不同的值**，且 `graph-source` 与 `graph`
> **图元数相同（375）而指纹不同** ⇒ 它连"只换了颜色"都能分辨。**报"相同"不是因为它分不出来。**

**结论与后果：**
- **4 条导航（`graph` / `graph-all` / `graph-backbone` / `graph-mvp`）指向同一张图**，
  而它们的说明文字承诺了三种不同的看法。**`graph-mvp` 白纸黑字写「实色高亮」「⊕ 虚线节点」——
  实测与普通图谱逐字节相同，那个高亮没有发生。**
- **2 条导航（`graph-solver` / `graph-loop`）指向同一张图**，同样各自承诺了不同内容。
- ⇒ **6 条导航条目只画了 2 张图。** 这是"功能重合"最严重的一处，
  且它比重合更糟：**屏上的文字与屏上的图不一致**。

### 2.4 设计品味：图谱九视角**没有视觉重心**

实测视口内最大字号 **12px**，而**并列拥有这个最大字号的元素有 109–119 个**。
一屏 117 个"最大字" = 一个重心都没有。对照我上一轮量的决策台：最大字号 42px，**独此一个**。

### 2.5 实体合并今天是一个**永远空着的导航位**

`main` 全文 **136 字**，逐字是「无待合并候选」+「暂无合并记录」，0 表行。
能力是真的（〔扫描候选〕按钮 + 两个真端点），但**在今天的数据下它永远是空的**。

## §4 · 诊断：为什么「完全看不懂他们之间的关系」

**页面边界是按「这是什么数据结构」切的，而用户是按「我要回答什么问题」找的。**

今天 20 个导航目的地的名字全是**名词**（关系 / 切片 / 切片库 / 建模 / 合并 / 边界 / 图谱×9），
**没有一个告诉用户"我什么时候该来这儿"**。三条实测后果：

1. **名字暗示的关系与事实相反**：「切片库」听起来是「本体切片」的目录，实测**交集 0**。
2. **同一件事有多个入口**：规划切片 2 个入口、子图面板 2 个挂载点、同一张图 4 条导航。
3. **一个页面装 5 件事**：本体关系 23,973 字，用户读不完也分不清哪块归哪块。

**还有一层更隐蔽的**：看懂前面所有东西的前提 —— **先看懂"一个具体对象长什么样、连着谁"**
—— 那个页面（对象视图）**恰恰是唯一没有导航入口的**。用户被要求先理解抽象（类型、关系、切片），
却拿不到具体（一个真实的常州基地对象）。

## §5 · 整合方案：20 个目的地 → **5 个页面 + 1 个画布**

### 5.1 切法与理由

**按「用户来这儿要回答什么问题」切。** 五个问题连成一条链，读一遍导航就懂顺序：

| # | 新页面 | 副标题（直接上屏） | 由今天的什么合成 |
|---|---|---|---|
| **①** | **本体总览** | 「**这个系统里有哪些东西**」 | 类型浏览 + 域管理 + 对象接口 + **对象视图入口** |
| **②** | **关系与规则** | 「**谁影响谁，影响多少**」 | 本体关系的**前两区**（结构边 + 因果边） |
| **③** | **取数路径** | 「**一次查询沿哪些关系走到哪些数据**」 | **本体切片 + 切片库合并** |
| **④** | **数据入本体** | 「**这些数据从哪来、怎么变成对象的**」 | 本体建模 + 实体合并 + 边界册治理 |
| **⑤** | **发布与体检** | 「**这次改动能不能发、谁得签字**」 | 本体关系拆出的：不变式 + 类型弃用 + 发布会签 + 版本 |
| **画布** | **本体图谱** | 「**把上面这些画出来**」 | 9 条图谱导航 → **1 条 + 视角切换器** |

**为什么是这个切法（四条理由，全部基于实测）：**

**理由一 · 合并的那两个，代码本来就是同一份。**
同一个 `SliceInspector`、同一个 `planSlice`、同一件用户的事。今天分两页的唯一根据是
**数据来源不同**（登记 vs 派生）—— 而"数据从哪来"是实现细节，**不该成为页面边界，
应该是页面内的一个筛选器**。

**理由二 · 拆走的那三个，与「边」没有共同的用户任务。**
判据：**「我改一条边」和「我发布一次本体」是同一次会话里的事吗？** 不是。
前者是日常建模，后者是变更管理（要会签、要跨域 owner）。叠一页的直接后果就是那 165 行。

**理由三 · 图谱不是模块，是视图。**
实测 9 条导航同一个端点 `GET /a/v1/ontology/graph`、只产出 5 张图。
**它们不是 9 个目的地，是一块画布的 5 种着色/过滤。** 一块画布 + 一个视角切换器，
既消掉 8 条导航，又让"这几个视角有什么不同"这件事**在同一屏内可比**——
今天要比两个视角必须来回点两条导航，**而其中 4 条根本是同一张图，用户比不出所以然**。

**理由四 · 把「具体」放在「抽象」前面。**
①「本体总览」排第一，且它是唯一一个能点到**真实对象**的地方。
先看懂常州基地这个对象有 19 条属性、连着 9 个数据源健康度，再去看类型/关系/切片，
才有参照物。今天的顺序恰好反过来。

### 5.2 各页第一屏该给什么、第二层收什么

沿用我在决策台上用的那套判据：**第一屏只放"数据 + 控件"，不放解说；
公式/机器名/规则码/口径说明一律进第二层（▸ 就地展开，不跳页不弹窗）。**

#### ① 本体总览 —— 「这个系统里有哪些东西」

```
本体总览
98 个对象类型 · 14 个域 · 1 个接口 · 12,740 个对象实例

[按域看] [按接口看] [找一个具体对象 ▸]
┌─ 工厂 (8 类型) ─┬─ 产品 (11) ─┬─ 工艺 (9) ─┬ … ┐
│ 生产基地  13 个实例  19 属性        │
│ 产线     130       12             │  ← 点一行 → 右侧就地出「这个类型」的详情
└──────────────────────────────────┘
```

- **第一屏**：四个计数 + 域分组的类型表（类型名 / 实例数 / 属性数）。
- **第二层（▸）**：`provenance` 来源数据集 · 派生公式 · 适用规则 · 接口实现关系。
- **关键新增**：类型行上的〔看一个实例 →〕直达对象视图 —— 这是今天唯一缺的那条链。
- ⚠ **不要**把 98 行一次铺完：今天类型浏览是 98 行平铺 + 4,856 字。按域折叠，默认只开最大的那个域。

#### ② 关系与规则 —— 「谁影响谁，影响多少」

```
关系与规则
结构边 114 条              因果边 42 条生效
「这两类东西之间有没有关系」  「A 的量变了，B 跟着变多少」
停用它 → 推演结果不变        停用它 → 推演结果会变
[结构边] [因果边]     ← 两个页签，不再同屏堆叠
```

- **这两句差别今天只在代码注释里**（`OntologyRelationsPage.tsx` 文件头「两种边，别混」写得很好），
  **屏上只有「两种边分开管：结构边 · 因果边」，没说差别**。把注释那两句**原样搬上屏** ——
  这是全案性价比最高的一处改动：两行字，消掉「停错边」这一整类事故。
- **第一屏**：两个计数 + 当前页签的表（按域折叠，默认收起）。
- **第二层**：系数/延迟/上界/衰减的来源（配置还是内联常数）· 引用反查 · 改动的波及面预览。
- **接分支**：`wo-ontology-edge-edit` 的 PUT/DELETE/PATCH + `change-impact-preview`
  落在「因果边」页签里，正好补上矩阵里「改/删因果边 ✗」那格。

#### ③ 取数路径 —— 「一次查询沿哪些关系走到哪些数据」

```
取数路径
能用的取数路径 65 条：人工登记 4 · 自动派生 61
另有 95 条单类型存根（每类型一条，只为覆盖率统计，不是取数路径）▸

来源：[全部 65] [人工登记 4] [自动派生 61] [存根 95]     [＋规划一条新路径]
```

- **「99」这个数以后不许单独出现。** 它把 4 条真路径和 95 条存根加在一起，
  **读者会得出与事实相反的结论**（以为有 99 条可用路径）。三个桶各自有名字、
  各自有一句话说明它是干嘛的，这个数才不骗人。
  > ⚠ 同一个病在别处也犯了：我上一轮实测决策台第二层原话是
  > 「本租户登记了 **99 条**切片」—— 同样没有拆分。**这两处该一起改。**
  > （95 条存根该留该删是数据工程师那份的题；无论留删，**第一屏都不该把它们和真路径加在一起报**。）
- 两个来源进**同一张表**，用一列「来源」区分；〔＋新建切片〕与〔规划〕页签**合成一颗按钮**
  （本来就是同一个 `planSlice`）；展开行仍用 `SliceInspector`（合并后只剩一个挂载点）。
- **第二层**：逐跳路径 · linkKeys · maxNodes · fixtures · 引用反查。

#### ④ 数据入本体 —— 「这些数据从哪来、怎么变成对象的」

```
数据入本体
9 个数据集 · 已映射 98 个类型 · 待合并候选 0 · 业务常数册 v1.0.0（3 册 22 条）
[源→类型映射] [同实体归一] [业务常数册]
```

- 三个页签对应今天的 本体建模 / 实体合并 / 边界册。**合并的理由**：这三件事回答的是同一个问题
  ——「进到本体里的这个数，可信吗、从哪来、口径是谁定的」。今天它们是三条并列导航，
  其中一条（实体合并）**永远是空的 136 字**，单独占一个顶层位不划算。
- **第一屏**：四个计数 + 当前页签内容。**空态要有话说** ——
  实体合并今天的「无待合并候选」应改成「**没有待归一的实体。上次扫描：从未扫描 ▸**」，
  否则用户分不清"扫过了没有"和"根本没扫过"（这正是我在决策台上定的那条诚实位判据）。

#### ⑤ 发布与体检 —— 「这次改动能不能发、谁得签字」

```
发布与体检
体检守卫 N 条通过 / M 条越线      待会签 K 件      当前版本 v…
[体检守卫] [类型弃用] [发布会签] [版本历史]
```

- 从今天的本体关系**原样搬走三个分区**，不改逻辑、不改端点，只换门牌。
- 顺带把 `/admin/interfaces` 的**发布门预览**挂到「体检守卫」页签里 ——
  它今天说的正是"此刻发布会不会被接口门拦"，与本页同一个问题。

#### 画布 · 本体图谱 —— 9 条导航 → 1 条 + 视角切换器

```
本体图谱                                    [视角 ▾ 对象层 / 产能推演 / 数据来源 / 求解器 / 智能体]
[域筛选：工厂 产品 工艺 设备 产能 质量 计划 外部]   [映射表]
```

- **视角切换器只保留实测真的不同的那 5 个**（对象层 / 产能推演 / 数据来源 / 求解器 / 智能体）。
- **`graph-all` / `graph-backbone` / `graph-mvp` / `graph-loop` 这 4 条不该继续作为独立导航**：
  实测它们与另一条逐字节相同。**两条路二选一** ——
  要么让它们**真的**渲染出承诺的样子（主干分级要真分级、MVP 要真高亮），
  要么**撤掉条目**，把那段说明文字并进对应视角的说明里。
  **⛔ 不许保持现状**：现状是"文字承诺了一种看法，图没有变" —— 这是屏上的假承诺。
- **视觉重心**：今天视口内 109–119 个元素并列最大字号（12px），**等于没有重心**。
  画布至少要让"当前视角高亮的那一族节点"在字号/明度上和其余拉开一档。

### 5.3 导航怎么放（沿用我定决策台那套判据）

```
▾ 本体与数据                       ← 组名从「建模与图谱」改为它现在真正装的东西
   本体总览          ← ①（含对象视图入口·排第 1 位：具体在抽象之前）
   本体图谱          ← 画布（吃掉旧 9 条图谱导航）
   关系与规则        ← ②
   取数路径          ← ③（吃掉旧「本体切片」+「切片库」）
   数据入本体        ← ④（吃掉旧「本体建模」+「实体合并」+「边界册治理」）
   发布与体检        ← ⑤（新，接旧「本体关系」拆出的三区）
   原型 intake       ← 保留（不在本轮范围）
```

**净变化：20 条导航目的地 → 7 条。**

三条判据（与我在 LOOP7 §12 定决策台入口时用的是同一套）：

1. **组名要说清这个抽屉里装什么。**「建模与图谱」今天装着建模、图谱、关系、切片、合并、
   边界、接口、类型 —— 名字只覆盖了其中两样。
2. **排序有意义，因为折叠态按用户持久化。** 我实测过（LOOP7 §12）：点一下组头折叠，
   `localStorage["nav.collapse.<组名>"]="1"`，**刷新后仍折叠**。⇒ 靠底部的条目会被真正看不见。
   所以排第 1 位的必须是"理解其余一切的前提"——那就是本体总览。
3. **一条导航 = 一个能站住的落地页。** 因此我**不建议**给 `/o/:type/:key` 本身加导航条目
   （它需要一个具体对象 id 才有意义）；对象视图的入口应该长在「本体总览」的类型行上。

## §7 · 一句话给仓主

> **您看不懂它们的关系，是因为今天这些名字描述的是「东西」不是「问题」。**
> **切完之后五个名字连成一句话：有哪些东西 → 谁影响谁 → 怎么取数 → 数据从哪来 → 能不能发。**
>
> **「功能重合」三处都实测坐实了，而且比"重合"更难看：**
> **9 条图谱导航只画出 5 张图（其中 4 条完全同一张，而 MVP 那条白纸黑字写着"实色高亮"、
> 图上没有）；两个切片页共用同一个面板同一个规划器，切片集合却毫不相干。**
>
> **「都缺了很多」也对，但缺的分两类：一类是页面没露出来（对象视图有页面没入口、
> 6 条域切片只差合分支）—— 很便宜；另一类是系统里压根没有（切片不能删、
> 没有共享属性类型、没有本体分支）—— 改页面没用，得单独立单。**
