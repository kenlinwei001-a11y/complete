# 系统本体「大脑」模式

本平台有一份自我元模型 `docs/SYSTEM-ONTOLOGY.md`，用平台自己的本体语言（对象类型 / 链路 / 规则 / 行动 / 检测 / 数据流）描述系统自身的接线。它是**系统接线的单一来源**。本 skill 强制把它作为分析前置。

## 第一步 · 强制读取（不可跳过）

在做任何分析、PRD、修复、回答"改 X 会影响什么"之前，**先完整读系统本体**：

1. 读本地 `docs/SYSTEM-ONTOLOGY.md`（仓库每会话克隆，是当前分支的真相源，等同 GitHub 上同一文件）。用 Read 工具读全文，不要只看摘要。
2. 若本地不存在，从 GitHub 拉取（兜底，注意分支可能漂移）：
   `https://raw.githubusercontent.com/kenlinwei001-a11y/complete/claude/vigilant-knuth-b1nmxn/docs/SYSTEM-ONTOLOGY.md`
3. 读完，在回复开头用一行声明：
   `已读系统本体 v<版本>，本次涉及：对象类型<…> · 链路<…> · 不变量<R…> · 断点<G…>`。
   读不到（本地与 GitHub 都失败）时，明确告知用户"未能加载系统本体，结论可能与实际接线不符"，不要假装读过。

## 第二步 · 分析协议（本体 §0 read-first）

严格按链路走，不要只看单个模块：

1. **定位对象类型**（§2）：这事涉及哪些制品（意图 / 执行计划 / 求解器 / 连接器 / 规则 / 场景卡 …）。
2. **沿链路追全链**（§3）：从入口到产出走一遍——**断点常在链路接缝，不在模块内部**。
3. **查不变量**（§5，R1–R12）：改动是否违反铁律（tenant_id / entitlement 先于 authz / 真值经 Action / 确定性 / 全链闭包 R11 …）。
4. **走检测门禁**（§7）：闭包门 / validate / 准备度 / A6 行级 / VLE / 断链审计——结论须说明该过哪些门。
5. **看数据流**（§4）：若是产出型操作，必须发对应领域事件、下游消费页必须订阅（D-29）。

核心戒律（写进每次分析的判断里）：**"绿测试 ≠ 能用"**——单元测试在 mock 下全绿，但链路接缝（跨服务形状、意图→计划接线、场景→答案闭合）断了测不出来。已知断点见 §8（G-1…G-8），先查它再下结论。

## 第三步 · 产出要求

- **任何 PRD / 架构变更必须包含《本体引用与影响》一节**：列出触及的对象类型 / 链路 / 事件 / 不变量，以及关闭或影响 §8 的哪些断点（G-1…G-8）。填不出这节 = 没真读本体，重来。
- **若改动新增或改变了链路 / 事件 / 对象类型 / 不变量 / 门禁 → 必须回写 `docs/SYSTEM-ONTOLOGY.md` 对应章节**（§2/§3/§4/§5/§8），本体是单一来源，不回写即过期失效。
- 命名禁用外部产品名（如 OntoFlow，是参考产品），用平台自有术语。

## 诚实边界（必须对用户透明）

- 本 skill **只在被显式调用时生效**，不保证"每次自动读"。要"无条件每次读"，需配 CLAUDE.md 铁律（每会话注入）+ SessionStart 钩子（harness 自动注入）。若用户在意"自动"，主动提示补这两项。
- 系统本体是 AS-IS 快照，`file:line` 锚点会随代码漂移；引用前若关键结论存疑，回代码核对一次。
